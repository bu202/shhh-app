## 2. 가입과 로그인의 흐름

### 2-0. 지금의 흐름 — **가입과 로그인은 갈라져 있다** (현재 사실)

⚠️ **2026-08-25 갱신.** 이 절은 오랫동안 아래 §2-1 의 **당시 흐름**을 현재형으로 설명하고
있었다. 그 흐름은 2026-08-18 에 없어졌고 `internalUid()` 라는 함수도 **삭제됐다** —
문서만 남아 「로그인이 곧 가입이다」를 현재 사실로 말하고 있었다.

```
[가입]
  POST /api/signup/start   → signupPossible() 확인 → 사람 확인(Turnstile) 검증
                           → 약관 수락·방침 표시·연령 진술을 **AES-256-GCM 으로 암호화**한
                             state 를 만들어 제공자로 보낸다(읽을 수 있는 상태로 안 지나간다)
  /api/cb|exchange/:name   → state 복호화 → 소비 표식(TOMBSTONE_KEY HMAC)으로 **1회용** 강제
                           → createAccountWithPolicy() 한 트랜잭션:
                               users 1행 + policy_events 3행 + sessions 1행
[로그인]
  GET  /api/login/:name    → loginPossible() 확인 → 서명 state 로 제공자로 보낸다
  /api/cb|exchange/:name   → findUser() **조회만 한다.** 계정이 없으면 만들지 않고
                             `#login=signup_required` 로 되돌려 가입 화면을 연다
```

| 지금 참인 것 | 근거 |
|---|---|
| **가입 화면과 절차가 있다.** 로그인 성공은 계정을 만들지 않는다 | `worker/index.js` 의 `POST /signup/start` · 콜백의 `findUser()` 갈래 |
| `internalUid()` 는 **존재하지 않는다** | 조회와 생성을 겸하던 함수라 삭제했다. 지금은 `findUser()`(조회)와 `createAccountWithPolicy()`(생성)가 별개다 |
| 약관·방침·연령을 **기록하는 표가 있다** | `policy_events` (migration `0005`). 필수 3종은 `terms/accepted` · `privacy/presented` · `age14/attested` |
| 그 기록은 **계정과 함께 지워진다** | `0005` 의 `ON DELETE CASCADE` (§21 결정 B) |
| 가입 state 는 **1회용**이다 | `consumed_signup_states` 의 소비 표식. 재사용은 `state_used` 로 거부 |
| 가입 정보가 제공자 URL 을 **평문으로 지나가지 않는다** | `SIGNUP_STATE_KEY` AES-256-GCM (설계서 §5-4) |
| 계정 삭제는 여전히 한 문장이다 | `DELETE FROM users WHERE id = ?` + CASCADE. 삭제 표식은 별도 ledger D1 |
| 로그인 화면이 **되지 않는 버튼을 그리지 않는다** | `loginPossible()`·`signupPossible()` 을 화면·시작·콜백이 **같은 함수로** 본다 |

⚠️ **이 절은 「원격에서 동작한다」는 뜻이 아니다.** 위 코드는 배포돼 있지만 계정 인프라가
미구성이라 계정 라우트는 **두 DB 를 만지기 전에 503** 이다. 현황의 원본은 `CLAUDE.md` §1-1.

### 2-1. **당시 사실(2026-08-17 이전)** — 자동 가입 흐름

아래는 이 문서를 쓸 당시 `worker/index.js` 를 읽어 확인한 것이고, **지금의 코드가 아니다.**
2단계가 다룬 문제의 뿌리를 남겨 두기 위해 보존한다.

```
/login/:provider          → shh_t 쿠키를 심고 SHA-256 을 state 에 서명해 제공자로 보낸다
제공자 동의 화면           → 요청 scope 0개 (구글만 openid)
/cb/:provider             → code 교환 **전에** shh_t 를 대조
exchange()                → 토큰 교환 → /me 호출 → 제공자 회원번호(who) 획득
                          → const uid = await internalUid(env, name, who);   ← 그때는 여기가 곧 가입이었다
                          → return await newSession(env, uid);
```

| 그때 확인한 사실 | 그때의 근거 |
|---|---|
| **회원가입 화면·절차가 없었다.** 소셜 로그인 성공이 곧 계정 생성이었다 | `exchange()` 가 분기 없이 `internalUid()` 를 불렀다 |
| `internalUid()` 는 **신규인지 기존인지 호출자에게 알려주지 않았다** | 두 경우 모두 `id` 문자열 하나만 돌려줬다 |
| 신규면 `crypto.randomUUID()` 기반 내부 ID 를 만들었다 | 같은 함수. 제공자 번호는 `users` 행 안에서만 산다 |
| 탈퇴 후 같은 제공자 계정으로 재가입하면 **새 내부 ID** 가 생긴다 | 행이 사라졌으므로 첫 `SELECT` 가 비고 새 UUID 를 만든다 (**지금도 참이다**) |
| 동의·약관·연령을 기록하는 자리가 **어디에도 없었다** | 그때 `users` 컬럼은 `id · provider · provider_subject · session_version · created_at` 뿐이었다 |

즉 그때는 **사용자가 "가입한다"고 인식할 순간 자체가 화면에 없었다.** 이것이 2단계가 다룬
문제의 뿌리이고, §3 이하의 결정은 전부 이 상태를 고치기 위한 것이다.

## 3. 확정된 회원가입 화면 정책

법률 검토 **전에** 확정되는 항목은 셋뿐이다.

| kind | action | 성격 |
|---|---|---|
| `terms` | `accepted` | 이용약관 **수락** |
| `privacy` | `presented` | 개인정보처리방침 **표시**(고지) |
| `age14` | `attested` | 만 14세 이상 **진술** |

세 가지는 법적으로 서로 다른 행위다. 하나의 "동의"로 뭉치지 않는다 — 고지를 동의로 기록하면
**받지 않은 동의를 받았다고 적는 것**이 된다.

### 승인된 화면 구성

```
┌────────────────────────────────────────────┐
│  shhh! 시작하기                            │
│                                            │
│  ☐ (필수) 이용약관에 동의합니다      [전문] │
│  ☐ (필수) 만 14세 이상입니다               │
│                                            │
│  ── 개인정보처리방침 요약 ──────────────── │
│  · 받는 것: 제공자 회원번호, 단어장,       │
│    직접 지은 별명(선택), 세션              │
│  · 이름·이메일·전화번호·생년월일 안 받음   │
│  · 계정 삭제 시 주 서비스 DB 에서 즉시 삭제 │
│  [개인정보처리방침 전문]                   │
│                                            │
│        [ 가입하기 ]   [ 그만두기 ]         │
└────────────────────────────────────────────┘
```

> **2026-08-17 정정 — 삭제 문구.** 이 상자에 있던 「계정 삭제로 전부 지울 수 있음」은 같은 문서
> §8·§9(Time Travel·백업 복원으로 되살아난다)와 **정면으로 충돌한다.** 화면에 쓸 뜻은 이것이다:
>
> > 계정 삭제 시 주 서비스 DB 에서는 즉시 삭제합니다. 복구 이력의 보유기간과 복원 시 재삭제
> > 절차는 개인정보처리방침에 함께 안내합니다.
>
> 이것도 **최종 법률 문구가 아니다.** 실제 화면·방침 문장은 §21·§22 의 프로젝트 결정에 따라 확정했고, `privacy.html` 6차판이 현재 문구다.

### 법률 검토 전 **넣지 않는** 것

- ☐ 개인정보 수집·이용에 동의합니다
- `privacy / accepted` 이벤트
- ☐ 국외 이전에 동의합니다 · `xborder` 이벤트
- 전체 동의 체크박스
- 선택 동의를 필수처럼 보이게 하는 UI

이유: 개인정보 보호법 제15조 제1항에서 이 처리의 근거가 **제1호(동의)** 인지 **제4호(계약의 이행)**
인지가 갈리지 않았다. 근거가 계약 이행인데 동의 체크박스를 두면 **철회 가능한 동의처럼 보여**
사용자를 오도하고, 근거가 동의인데 안 두면 근거가 없다. 둘 중 어느 쪽인지는 §6 의 질문이다.

국외 이전도 같다. 제28조의8 제1항 **제1호(별도 동의)** 인지 **제3호(계약 이행을 위한 처리위탁·보관 +
방침 공개)** 인지 확정된 뒤에 설계한다.

## 4. `policy_events` v2 — 설계 승인, **생성은 연기**

### 승인된 설계

```sql
CREATE TABLE policy_events (
  id               INTEGER PRIMARY KEY,
  user_id          TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  kind             TEXT NOT NULL,
  action           TEXT NOT NULL,
  document_version TEXT NOT NULL,
  recorded_at      INTEGER NOT NULL,
  CHECK (
    (kind = 'terms'   AND action = 'accepted') OR
    (kind = 'privacy' AND action = 'presented') OR
    (kind = 'age14'   AND action = 'attested')
  )
);

CREATE INDEX policy_events_user
  ON policy_events(user_id, kind, id DESC);
```

- 복합 `CHECK` 를 쓴 이유: `kind` 와 `action` 을 따로 검사하면 `('age14','accepted')` 같은
  **말이 안 되는 조합이 통과**한다. 셋만 허용해 DB 가 조합 자체를 강제한다.
- `granted`·`withdrawn`·`xborder` 는 스키마에서 **제외**한다. `granted` 는 고지를 동의로 만들고,
  `withdrawn` 은 지금 쓸 자리가 없으며, `xborder` 는 근거가 미확정이다.

### 이번 단계에서 만들지 않는 것

`policy_events` 테이블 · migration 파일 · `worker/schema.sql` 변경 · 가입 API · 가입 UI ·
`scripts/test-policies.mjs`.

### 왜 지금 만들지 않는가 (2026-08-17 시점의 판단 — **2026-08-18 에 해소됐다**)

⚠️ **아래는 당시 사실이다.** 근거가 확정되지 않아 `CHECK` 목록을 정할 수 없었다.
2026-08-18 에 제15조 제1항 제4호로 확정하면서 `migrations/0005` 를 만들었다(§21).

1. ⚠️ 법적 근거가 확정되면 `privacy/accepted` 의 필요 여부가 달라지고, 그러면 **`CHECK` 안의 목록이 바뀐다.**
   (2026-08-18 에 계약 이행으로 확정되면서 이 항목은 `privacy/presented` 하나로 정해졌다.)
2. **SQLite 는 기존 `CHECK` 제약을 `ALTER` 로 바꿀 수 없다.** 바꾸려면 새 테이블을 만들어 옮기고
   옛 테이블을 지우는 재생성 migration 이 필요하다 — `0003` 이 이미 한 번 한 일이다.
3. 따라서 **아직 한 행도 쓰지 않는 테이블에 재생성 migration 을 쓰게 된다.** 이력만 늘고 얻는 것이 없다.

### 남겨 둔 재검토 항목

정책 이벤트를 계정 삭제 후에도 일정 기간 보존해야 한다는 법률 검토 결과가 나오면
`ON DELETE CASCADE` 를 다시 검토해야 한다. **현재 승인된 것은 계정과 함께 지우는 최소 수집 방향뿐**이다.

## 5. `document_version` 무결성 요구사항 (3단계 필수 조건)

`document_version` 은 사람이 손으로 적는 `v1`·`v2` 가 아니라 **사용자가 실제로 본 불변 문서 내용의
SHA-256 해시**다. 손으로 적는 번호는 "사용자가 본 글"과 "우리가 기록한 번호"가 조용히 갈라진다.

| # | 요구사항 |
|---|---|
| 1 | 공개한 약관·방침·연령 문구를 버전별 **불변 파일**로 보존한다 |
| 2 | 기존 버전 파일을 **덮어쓰지 않는다.** 고칠 때는 새 버전 파일을 추가한다 |
| 3 | manifest 가 `종류 · 파일 경로 · SHA-256` 을 잇는다 |
| 4 | 서버는 **manifest 에 등록된 해시만** 기록한다 |
| 5 | 클라이언트는 `document_version` 과 `recorded_at` 을 **지정하지 못한다** |
| 6 | `recorded_at` 은 서버 시각(`Date.now()`)이다 |
| 7 | `scripts/test-policies.mjs` 가 실제 파일 해시와 manifest 를 대조한다 |
| 8 | 내용이 바뀌었는데 manifest 가 그대로면 **테스트가 실패한다** |
| 9 | 계정 생성과 정책 이벤트 기록은 **같은 `batch()`** 로 원자적으로 처리한다 |

이번 단계에서는 요구사항만 확정하고 파일도 테스트도 만들지 않는다.

## 7. 만 14세 이상 정책과 남은 질문

**확정된 것**: 만 14세 이상만 로그인할 수 있다. 로그인 없이 둘러보기는 나이 제한이 없다.
가입 화면에서 `age14 / attested` 로 **진술**을 받는다.

**확정되지 않은 것**:

- 생년월일을 제공자에게 요청하지 않으므로 **나이를 확인할 수단이 전혀 없다.** 이 제한은
  기술적 차단이 아니라 진술이다. `privacy.html:174-176` 이 이 사실을 이미 적고 있다.
- 확인 수단을 만들려면 생년월일이나 본인확인을 받아야 하는데, 그것은 **최소수집 원칙과 정면으로 충돌**한다.
  둘 중 무엇을 택할지는 법률 검토 결과에 달렸다(L6).
- 개인정보 보호법 제22조의2(시행 2023-09-15)는 만 14세 미만에 대해 법정대리인 동의 **및 확인**을
  요구한다. 우리는 만 14세 미만을 받지 않는 설계지만, **받지 않는다는 진술만으로 충분한지**는 미확인이다.

## 8. Time Travel 복원 시 삭제 계정 부활 위협

### 사실

- Cloudflare D1 의 Time Travel 은 **항상 켜져 있고 끌 수 없다.**
- 운영자는 `wrangler d1 time-travel restore` 로 과거 시점을 되살릴 수 있다. **우리가 통제할 수 없는
  기능이 아니다** — 우리가 실행할 수 있는 기능이고, 그래서 우리 절차의 문제다.
- 복원은 **제자리 덮어쓰기**이며 파괴적이다. 다만 실행 결과로 받은 bookmark 로 되돌릴 수 있다.

### 위협

사용자가 계정을 삭제한다 → 며칠 뒤 운영자가 다른 이유로 복원한다 → **삭제된 계정·단어장·별명·
친구 관계·초대 코드가 전부 되살아난다.** 친구 목록에 다시 나타나고 별명이 다시 보인다.

즉 `privacy.html:73` 의 "지우시면 그 자리에서 사라집니다"는 **복원을 하면 거짓이 된다.**

### 검토했다가 **기각한** 대안

| 대안 | 왜 안 되는가 |
|---|---|
| 복원 후 전원 재로그인만 시킨다 | **당시(2026-08-17): `internalUid()` 가 살아남은 행을 찾아 돌려줬다.** 지금 그 함수는 없지만 결론은 그대로다 — `findUser()` 가 복원된 행을 찾아 주므로 재로그인은 탈퇴자를 원래 계정으로 되돌린다 |
| Time Travel 대신 수동 백업만 쓴다 | 백업 복원도 **똑같이 부활시킨다.** 문제는 복원 수단이 아니라 복원 자체다 |
| 재가입 시 새 무작위 ID 가 생기는 성질에 기댄다 | 그건 **재가입한 사람**만 보호한다. 탈퇴하고 돌아오지 않은 사람은 그대로 부활한다. **보조 보호일 뿐 주 방어책이 아니다** |

## 9. pending / confirmed 삭제 표식 설계 방향 (3단계)

**채택한 방향**: 복원 대상인 주 D1 **밖에** 최소 삭제 표식을 보관하고, 복원 전후에 **확정된** 표식을
재적용한다.

| # | 요구사항 |
|---|---|
| 1 | 주 D1 과 **별도인 저장소**에 전용 삭제 표식을 기록한다 |
| 2 | 원본 제공자 ID · 이메일 · 별명 · 단어장 · 세션을 **저장하지 않는다** |
| 3 | **전용 비밀키로 내부 UID 를 HMAC 한 값만** 저장한다 |
| 4 | `RL_KEY` · `STATE_KEY` · OAuth secret 을 **재사용하지 않는다** — 하나를 교체할 때 다른 하나가 같이 무너진다 |
| 5 | 상태를 `pending` 과 `confirmed` 로 구분한다 |
| 6 | 순서: **pending 기록 → 주 D1 계정 삭제 → 계정 행 부재 확인 → `confirmed_at` 기록** |
| 7 | 주 D1 삭제가 **실패한 pending 표식은 복원 후 삭제에 쓰지 않는다** |
| 8 | 삭제는 성공했는데 `confirmed_at` 기록만 실패한 경우를 되살릴 **reconciliation 절차**를 둔다 |
| 9 | 모든 DB 복원은 **maintenance mode 에서만** 수행한다. ⚠️ **3판 정정: maintenance mode 는 「새 요청의 진입」만 막는다.** 이미 진입한 요청까지 빠져나갔음을 확인하는 **전역 write drain 이 따로 필요하고, 그것이 아직 없어 주 D1 복원은 금지다**(3단계 설계서 §10-8-0·§10-9-6) |
| 10 | 복원 **전에** 현재 주 D1 과 pending 표식을 대조해 삭제 성공 여부를 확정한다 |
| 11 | 복원 **후에** confirmed 표식과 일치하는 부활 계정을 다시 삭제한다 |
| 12 | 재삭제와 CASCADE 결과를 확인한 **뒤에만** 서비스를 재개한다 |
| 13 | **confirmed** 표식은 `max(TIME_TRAVEL_WINDOW, BACKUP_MAX_AGE) + SAFETY_MARGIN` 을 `confirmed_at` 부터 세어 넘긴 뒤 폐기한다. **5판 정정 — 수동 백업도 계정을 되살리므로 Time Travel 만 보면 안 된다.** 현재 계산값은 **15일**이다(2026-08-26 재계산 · Free 요금제 · §24-3). ⚠️ **여전히 기술적 계산값이고 법정 보유기간이 아니다.** ⛔ 2026-08-26 전에는 37일이었고 그것은 Time Travel 30일을 **가정**한 값이었다. **pending 표식은 시간으로 폐기하지 않는다** — 설계서 §10-5·§10-5-1 |
| 14 | 플랜이 미확인이므로 **복원 가능 최대 기간**의 안전 기준은 **최대 30일**을 쓴다(표식 보유기간이 아니라 그 산식의 입력값이다). ⚠️ **`privacy.html` 에 「N일 뒤 삭제」를 단정하지 않는다** — 산식의 네 항이 확정되고 법률 검토가 끝난 뒤에 문장을 만든다 |
| 15 | 표식보다 오래된 수동 백업을 남기지 않는다. 폐기할 수 없으면 **restore 금지 대상으로 명시 분류**한다(설계서 §10-5 의 B1·B2 · 법률 `L14`) |

**7번이 왜 있는가**: 표식만 남고 D1 삭제가 실패하면, 사용자는 계정이 살아 있어 계속 쓴다.
그 상태에서 나중에 복원하면 **표식이 살아 있는 계정을 지운다.** `confirmed` 만 재적용하는 규칙이
그 사고를 막는다.

**legacy KV 를 이 저장소로 재사용하지 않는다.** KV 는 §11 에서 폐기하기로 한 자원이고,
지우기로 한 곳에 새 책임을 얹으면 폐기가 영원히 미뤄진다.

이번 단계에서는 별도 DB·KV·테이블·시크릿을 **만들지 않는다.** 설계 요구사항만 확정한다.

## 10. 수동 백업 규칙

| 규칙 |
|---|
| 원격 migration **직전에만** 생성한다. 상시 백업은 금지 |
| 저장소와 Git **밖에** 둔다 |
| 암호화된 로컬 볼륨을 쓴다 |
| 일반 클라우드 동기화 폴더에 평문으로 두지 않는다 |
| 생성 시각 · 목적 · 해시 · **삭제 예정 시각**을 기록한다 |
| 로컬 복원 시험을 수행한다(백업이 실제로 살아나는지) |
| migration 과 smoke test 성공 후 **24시간이 지나면** 삭제한다 |
| 어떠한 경우에도 **7일을 넘겨 보관하지 않는다** |
| 복원할 때는 Time Travel 과 **동일한 삭제 표식 재적용 절차**(§9)를 쓴다 |
| 삭제 표식 보유기간보다 오래된 백업을 만들지 않는다 |

"migration 성공 즉시 삭제"로 하지 않는 이유: 스키마 오류는 즉시 드러나지만 **데이터 오류는 늦게
드러난다.** 24시간은 최소한 하루치 실사용을 관찰할 시간이다. 7일 상한은 그 반대 방향의 제동이다 —
백업은 곧 평문 단어장·별명 사본이라 오래 둘수록 그 자체가 위험이다.

## 11. KV 폐기 6단계 (방향 승인, 이번 단계에서는 삭제하지 않음)

현재 확인된 legacy KV 상태 (**접두사별 개수만** 셈. 2026-08-16 승인된 읽기 전용 조회 →
2026-08-17 Codex 재집계에서 같은 값. **이 문서를 쓰면서 다시 세지는 않았다** — 값이 같았고
KV 는 새 코드가 쓰지 않아 변할 이유가 없다):

| 접두사 | 개수 |
|---|---|
| `b:` | 1 |
| `c:` | 1 |
| `s:` | 2 |
| `u:` | 1 |
| **합계** | **5** |

값과 전체 키 이름은 **확인하지 않았다.** 값 확인은 불필요하다 — 개수만으로 "KV 시대에 계정이 하나
있었다"는 사실이 확인되고, 그것이 판단에 필요한 전부다. `kv key get` · 삭제 · 수정은 하지 않았다.

**확정된 순서**:

| # | 단계 |
|---|---|
| 1 | KV 기반 과거 배포로의 **롤백을 공식적으로 금지**한다 |
| 2 | 현재 D1 세대에서 쓸 수 있는 **배포 롤백 절차**를 확정한다 |
| 3 | 원격 D1 migration 과 현재 코드 세대가 **일치하는지 검증**한다 |
| 4 | `wrangler.jsonc` 의 KV 바인딩과 문서의 KV 의존 설명을 제거한다 |
| 5 | KV 없는 배포를 **별도 승인 후** 실행하고 smoke test 한다 |
| 6 | 사용자의 **파괴적 작업 최종 승인**을 다시 받은 뒤 namespace 를 삭제하고 0개를 확인한다 |

1번이 먼저인 이유: 지금 KV 바인딩이 남아 있는 유일한 근거가 "옛 배포로 롤백하면 그 코드가 KV 를
읽는다"(`wrangler.jsonc:22-24`)이다. 그 근거를 **먼저 명시적으로 폐기하지 않으면** 4번을 할 때
"롤백 경로를 몰래 없앴다"가 된다.

**KV 는 아직 살아 있다. 이번 단계에서 지우지 않았다.**

## 21. 2026-08-18 프로젝트 결정 — §16 착수 조건의 해소

⚠️ **먼저 분명히 한다.** 아래는 **사용자가 공식 자료와 실제 공개 사례를 검토해 내린 프로젝트
운영 결정**이다. **외부 법률 검토 완료가 아니고, 법적 적합성 보증도 아니다.**
법령 변경·사업 확장·유료 결제·민감정보 수집·아동 대상 서비스가 생기면 재검토한다.
현재 이메일·전화번호·생년월일·결제정보·민감정보를 추가 수집하지 않는다.

### 21-1. 확정된 것

| # | 항목 | 결정 | 근거로 채택한 조문 |
|---|---|---|---|
| A | 서비스 제공에 필수인 처리의 근거 | **계약의 이행** | 「개인정보 보호법」 제15조 제1항 **제4호** |
| B | `policy_events` 의 계정 삭제 시 처리 | **ON DELETE CASCADE**(계정과 함께 삭제) | 최소보유 원칙. 탈퇴자 가명키 보존 구조를 만들지 않는다 |
| C | Cloudflare 국외 처리위탁·보관 | **별도 동의를 받지 않는다** | 제28조의8 제1항 **제3호** |
| D | 만 14세 미만 | **가입 대상에서 제외.** 법정대리인 동의 절차를 만들지 않는다 | 필수 진술 1개. 본인확인은 하지 않는다 |
| E | 외부 법률 검토(L1~L16) | **4단계 착수 게이트에서 제외.** *(당시 결정. 2026-08-26 에 §22 로 개정돼 공개 출시 조건에서도 빠졌다)* | — |

### 21-2. 그래서 §16 의 다섯 조건이 이렇게 됐다

| # | §16 의 조건 | 지금 |
|---|---|---|
| 1 | 개인정보 처리의 법적 근거 확정 (L1·L2) | ✅ 프로젝트 결정 A |
| 2 | 국외 이전 근거 확정 (L3·L4) | ✅ 프로젝트 결정 C |
| 3 | `policy_events` 최종 `CHECK` 목록 확정 | ✅ `terms/accepted` · `privacy/presented` · `age14/attested` — `migrations/0005` |
| 4 | 아동 정책의 법률적 적정성 (L6) | ⚠️ **법적 적정성은 확인되지 않았다.** 방침만 확정했다(결정 D) |

### 21-3. 확정되지 **않은** 것 — 여전히 열려 있다

| 항목 | 상태 |
|---|---|
| 국외 처리의 **실제 국가 특정** | ⚠️ **못 했다.** Cloudflare 는 위치를 국가가 아니라 지역으로 알려준다. 우리 D1 은 `running_in_region: APAC` · `jurisdiction: null` 이다(2026-08-18 읽기 전용 확인). **APAC 은 국가도 관할권도 아니다.** `privacy.html` 에 확인한 것과 확인 못 한 것을 나눠 적었다 |
| 복구본·삭제 표식의 **보유기간** | ✅ **정했다(2026-08-26 · §24-3).** 요금제(Workers Free — 사용자 확인)와 백업 규칙(migration 직전에만 · R2 7일 만료)이 확정돼 `CONFIRMED_RETENTION` 을 **15일**로 재계산했고, 방침이 복원 창(최대 7일)과 표식 보유(약 15일)를 적는다. ⛔ **「N일 뒤 반드시 삭제」는 여전히 안 적는다**(R2 삭제 지연) · ⛔ **유료 전환 시 재계산 게이트**가 걸린다 |

| 외부 전문가 상담 | **해당 없음 — 필수 범위에서 제외**(§22). ⚠️ **법적 적합성 보증이 아니다** |

### 21-4. `privacy.html` 불일치 — §14 의 처리 결과

| # | §14 항목 | 처리 |
|---|---|---|
| 1 | 둘러보기가 「아무 정보도 수집하지 않는다」 | ✅ 「로그인하지 않아도 남는 것」 절을 새로 만들어 호스팅 접속 기록·국립국어원 요청·리미터 변환값 셋을 적었다 |

  **법령·사례 자체 검토 자료**이고, L1~L16 은 세 상태로 분류돼 살아 있다(§22).

> 대신 **공식 법령 → 정부·공공기관 공식 설명 → 실제 운영 서비스의 공식 개인정보처리방침·가입 화면**

### 22-3. 그래서 이렇게 쓴다

| 쓰는 말 | 쓰지 않는 말 |
|---|---|
| 외부 전문가 상담: **해당 없음 — 사용자 결정으로 필수 범위에서 제외** | 외부 법률 검토 미완료이므로 No-Go |
| 공식 법령과 실제 서비스 사례로 **프로젝트 방침을 확정**했다 | 변호사 검토 완료 · 외부 법률 검토 완료 |
| **법적 적합성은 보증하지 않는다** | 법적으로 완벽하다 · 법적 문제가 전혀 없다 |

### 22-4. 이 결정이 바꾸지 **않은** 것

- **공개 OAuth·계정 출시는 여전히 No-Go 다.** 사유는 §17 의 기술·운영 항목(원격 계정 인프라 ·

  생기면 재검토한다(§22-5).

### 22-5. 재검토를 다시 여는 조건

### 24-6. 국외 이전 — 무엇을 확인했고 무엇을 못 했나

**확인한 사실**(원본과 확인 날짜는 `docs/PRIVACY_LEGAL_REVIEW_PACKET.md` §15):

- D1 의 **location hint 는 실제 위치를 보장하지 않는다**(공식 문서).
- D1 의 **jurisdiction 은 `eu` · `fedramp` 둘뿐**이고 **한국은 없다.**
- jurisdiction 은 **만들 때만** 지정할 수 있어 **기존 D1 에 나중에 붙일 수 없다.**
- 우리 D1 은 `running_in_region: APAC` · `jurisdiction: null` 이다.

**결정한 운영안:**

| 항목 | 결정 |
|---|---|
| 구조 | 현재 Cloudflare 구조를 **유지한다** |

⛔ **처리 요청의 실제 내용을 Git 에 저장하지 않는다.** 별도 관리 방식은 이렇다.

| # | 규칙 |

| 1 | 문의 **원문은 전용 개인정보 이메일함에만** 둔다 |

**처리 목표 기간:** 받은 날부터 **10일** 안에 처리·회신. 더 걸리면 사유와 예상 시점을 먼저 알린다.

## 25. 2026-08-26 2단계 보완 — **방침이 없는 기능을 가리키고 있었다**

§24 를 닫은 뒤, **방침 문장을 코드와 한 줄씩 대조**했다. 여섯이 나왔고 그중 넷은
성질이 다르다 — **코드 결함이 아니라 「약속한 기능이 존재하지 않았다」**이다.
위협 번호와 상세 재현은 `docs/STAGE3_SIGNUP_SECURITY_DESIGN.md` 의 **0-16 절**(위협 73~78)이 원본이다.
여기에는 **2단계 결정으로서 무엇이 확정됐는지**만 적는다.

### 25-1. 열람권은 **파일로 받을 수 있어야 한다**

| 결정 | 내용 |
|---|---|
| 무엇을 | 계정 번호 · 제공자 회원번호 · 가입 시각 · 별명 · 단어장 · 친구 관계 · 초대 코드 · 가입 기록 · 세션 메타데이터 · 처리정지 상태 |
| ⛔ 무엇을 **안** | 친구의 제공자 회원번호 · 친구의 단어장 · 세션 토큰과 그 해시 · 어떤 비밀값도 |
| 0건과 누락 | **구분한다** — 값이 없어도 키는 `[]`·`null` 로 있고 `건수` 를 따로 적는다 |
| 캐시 | `no-store` · 첨부. 한 기기를 두 사람이 쓰는 경우가 실재한다 |

### 25-2. 처리정지는 **로그아웃도 삭제도 아니다**

| 축 | 로그아웃 | **처리정지** | 계정 삭제 |
|---|---|---|---|
| 세션 | 전부 끊긴다 | 전부 끊긴다 | 전부 끊긴다 |
| 계정·단어장·친구 | **남는다** | **남는다** | 지워진다 |
| 친구에게 보이나 | **보인다** | ⛔ **안 보인다** | 안 보인다 |
| 되돌릴 수 있나 | — | **재개로 되돌린다** | ⛔ 못 되돌린다 |

- 재개는 **OAuth 재인증 + 사용자의 명시적 선택 + 1회용 티켓**이다.
  ⛔ **로그인 성공만으로 재개하지 않는다** — 그러면 정지가 사실상 존재하지 않는다.
- 취소하면 **아무 요청도 나가지 않고** 정지가 유지된다(티켓은 10분 뒤 스스로 만료).
- 정지 중 삭제하시려면 **먼저 재개**하셔야 한다. 재개는 클릭 한 번이라 벽이 아니고,
  파괴적 작업을 1회용 티켓만으로 실행하지 않기 위해서다.

### 25-3. 이메일은 **접수 수단이지 소유 증명이 아니다**

- 이 앱은 이메일을 **요청하지도 저장하지도 않는다.** 그러므로 보낸 사람과 계정을
  **안전하게 이을 값이 없다.**
- ⛔ **이메일만으로 열람·정정·삭제·정지 해제를 하지 않는다.** 하면 그것이 곧
  남의 계정을 여는 통로다.
- 로그인이 안 되면 **제공자 계정 복구가 먼저**다.
- ⛔ 본인확인에 **실명·전화번호·신분증을 새로 받지 않는다.**
- ⛔ 운영자가 임의 SQL 로 「아마 이 사용자」를 찾아 지우는 절차를 **만들지 않는다.**

### 25-4. 백업은 **아직 운영하지 않는다** — 방침이 그렇게 적는다

- 도구는 있다(`scripts/backup.mjs`). **R2 버킷도 키 파일도 없다** → 지금은 `config` 로 fail-closed.
- 방침은 **「지금 운영하고 있지 않습니다 · 만들어진 백업 사본은 하나도 없습니다」**라고 적는다.
  실제로 운영을 시작하면 **그 문단을 먼저 고친다.**
- ⛔ **자동 복원 경로를 만들지 않는다.** ⛔ **정기(매일) 백업을 하지 않는다.**
- ⛔ **백업 성공이 migration 승인을 대신하지 않는다.**

### 25-5. 삭제 표식의 **15일은 최소값이다**

지우는 조건은 **넷을 모두 만족할 때**다 — 확정됐고 · 최소 보유기간이 지났고 ·
**복원 창을 벗어났고** · **담고 있을 수 있는 백업이 없음을 확인**했을 때.
⛔ **확인하지 못하면(모르면) 지우지 않는다.**

⚠️ 복원 창은 요금제가 정한다(`D1_PLAN`). **모르는 값은 가장 긴 30일**로 떨어진다 —
빠뜨리면 표식이 더 오래 남을 뿐이라 안전한 방향이다. 위험한 방향(유료인데 `free` 로
적힌 채)은 코드가 못 막으므로 **요금제 전환이 운영 게이트**다.

### 25-6. 늘어난 원격 게이트 — **넷 다 이번 세션에서 실행하지 않았다**

| 새 것 | 없으면 |
|---|---|
| 주 D1 migration **`0007`** | 처리정지·재개·친구 가리기가 SQL 오류 |
| ledger migration **`0005`** | 정리 크론이 표식 정리에서 **의도된 실패** |
| vars **`D1_PLAN`** | 표식이 30일 기준으로 더 오래 남는다(안전한 방향) |
| R2 비공개 버킷 · 암호화 키 파일 | 백업이 `config` 로 fail-closed — **migration 을 돌리면 안 된다** |

절차는 `docs/OPS_RUNBOOK.md` §6-4 · §6-5 · §4-1 · §18-2 다.

⚠️ **이 절도 법적 적합성 보증이 아니다.** 여기 적은 것은 **프로젝트 운영 결정**이고,
그 결정이 코드에서 실제로 그렇게 도는지는 `scripts/test-rights.mjs`·`scripts/test-backup.mjs`·
`scripts/test-policies.mjs` 검사 14 가 잰다.

## 26. 2026-08-27 2단계 재마감 — **방침 세 문장이 코드와 반대였다**

§25 를 닫은 뒤 3·4단계 재검토와 함께 방침을 다시 대조했다. 이번에 나온 것은 「없는 기능을
가리켰다」가 아니라 **있는 기능을 반대로 설명했다**는 성질이다 — 그래서 더 조용하다.

| # | 방침이 말한 것 | 코드가 하는 일 | 어떻게 고쳤나 |
|---|---|---|---|
| 1 | 「로그아웃은 **이 기기의** 접속을 끝내는 것」 | `killSessions()` 가 `session_version` 을 올리고 그 계정의 `sessions` 행을 **전부** 지운다 → **모든 기기**가 끊긴다 | 방침·요약을 「로그인돼 있는 **모든 기기**의 접속을 한꺼번에 끝냅니다」로 고쳤다 |
| 2 | 한 줄 요약: 「계정도, **단어장도**, 별명도 만들지 않습니다」 | 서버에는 안 만들지만 **기기 안에는 만든다**(`BOOK_KEY = "shh-wordbook"`). 같은 문서가 몇 문단 뒤에서 **반대로** 적고 있었다 | 「**저희 서버에는** … 만들지 않습니다 · **이 기기 안에는 단어장이 만들어집니다**」로 한정 |
| 3 | 나이 절: 「계정·단어장·별명 어느 것도 만들지 않습니다」 | 같음 — ②와 **같은 거짓이 한 번 더** 있었다 | 같은 방식으로 한정. ⚠️ **새 검사가 이걸 잡았다** — ②만 고쳤으면 그대로 남았다 |

### 26-1. 되살아나지 않게 만든 방법

  지우는지를 소스에서 본 **뒤에** 방침을 잰다. 코드가 바뀌면 검사가 먼저 실패한다.

  옛 문장을 그대로 둔 문서가 통과한다 — 그러면 **문서가 스스로 모순인 채로 초록불**이 된다.
- 「단어장을 만들지 않는다」류는 **전부 훑어** 하나하나가 「서버」로 한정돼 있는지 본다.
  ③이 그렇게 잡혔다.

돌연변이 **D41·D42·D43** 이 세 문장을 각각 되돌리고, 셋 다 `test-policies` 에서 사망한다.

## 27. 2단계 재대조 — 보관함 분류와 처리정지 약속 (2026-08-27)

### 27-1. 방침 문장 ↔ 코드 대조 — **바꾼 문장은 없다**

이번 회차에 방침 문장을 하나도 고치지 않았다. 고친 것은 **코드 쪽**이다 —
「처리정지를 누르면 **모든 기기에서 로그인이 풀린다**」는 약속이 세션을 지우는 것만으로는
지켜지지 않는다는 것이 드러났기 때문이다(위협 82).

| 방침이 말하는 것 | 그것을 지키는 코드 | 검사 |
|---|---|---|
| 처리정지 → **모든 기기에서 로그인이 풀린다** | `suspendAccount` 가 세션 삭제 + 세대 증가를 **한 batch** 로 하고, **그 뒤 도착한 콜백도 세션을 만들 수 없다**(발급 문장의 `suspended_at IS NULL`) | `test-policies` 17 · `test-actor-fence` F12·F15·F16 |
| **로그인만으로는 자동으로 다시 시작되지 않는다** | 정지 계정의 콜백은 세션을 안 만들고 1회용 재개 티켓만 심는다 | `test-rights` E3·E4 |
| 로그아웃 → **로그인돼 있는 모든 기기** | `killSessions` 가 세대를 올린다 | `test-policies` 15-a |

⚠️ **`test-policies` 17 은 방침과 코드를 함께 잰다** — 한쪽만 고치면 실패한다.
문장이 코드보다 강한 보장을 주장하지 않는지 확인하는 자리가 여기다.

### 27-2. 정책 보관함의 current / past / draft (K4)

`policies/index.html` 이 `versions` 전체를 「지난 판」으로 뿌려서 **지금 나가는 사본 넷이
「지난 판」에도** 있었다. 보관함의 쓸모는 「그때 그 사람이 본 문서가 이것이다」인데,
현재 판이 섞이면 그 지목이 안 된다.

이제 셋으로 나눈다:

| 구분 | 뜻 | 실측(2026-08-27) |
|---|---|---|
| **지금 쓰이는 문서** | 번들(`pv`)이 가리키는 사본 | 4개 |
| **지난 판 — 실제로 나갔던 문서** | 배포 경계(`e02e810`) 시점에 저장소에 있던 것 | **3개** |
| **아직 나간 적 없는 판** | 로컬에서 stamp 만 됐다 — **아무도 본 적이 없다** | **8개** |

⛔ **불변 사본의 바이트는 하나도 고치지 않았다**(`test-policies` 16-e 가 이름의 해시와
내용을 전수로 대조한다). 분류만 바꿨다.
⚠️ 경계의 원본은 `scripts/deployed.mjs` 의 source 해시이고, 분류는 `git ls-tree` 로 파생한다 —
manifest 에 적어 두면 그 값이 낡는다.

## 28. 2단계 정책 문서 최종 마감 — 제공자 상태를 세 문서가 같게 말한다 (2026-08-31)

### 28-1. 무엇이 어긋나 있었나

세 문서가 **같은 사실을 서로 다르게** 적고 있었다. 코드의 원본은 `ENABLED_PROVIDERS`
하나이고 초기 개방 목록은 네이버·카카오인데, 문서는 이렇게 갈려 있었다.

| 문서 | 옛 문장의 뜻 | 무엇이 틀렸나 |
|---|---|---|
| `policies-src/terms.html` 제4조 | 「가입에는 **카카오·네이버·구글** 로그인을 씁니다」 | 구글은 초기 개방 목록 밖이다(2026-08-26 결정). 서버가 `isProvider()` 한 자리에서 막는다 |
| `privacy.html` | 「**지금 쓰실 수 있는** 로그인 방법은 네이버와 카카오 둘입니다」 | 계정 기능 자체가 아직 열려 있지 않다 — 지금은 둘 다 쓸 수 없다 |
| `policies-src/summary.txt` | 「**지금 쓰실 수 있는 것은** 네이버와 카카오 둘입니다」 | 같음 |

⚠️ **셋 다 「구글이 열려 있다」와 「네이버·카카오가 지금 열려 있다」라는 서로 다른 두 거짓을
섞고 있었다.** 앞의 것은 2026-08-26 결정과, 뒤의 것은 현재 배포(계정 라우트 fail-closed)와 어긋난다.

### 28-2. 세 문서가 지금 함께 말하는 것

1. **현재 계정 기능은 열려 있지 않다** — 지금은 가입도 로그인도 되지 않는다.
2. **계정 기능을 여는 날 처음 지원할 것은 네이버와 카카오다.**
3. **구글 로그인은 초기에는 지원하지 않는다** — 구현은 남아 있지만 서버도 받지 않는다.
4. 이름·이메일·전화번호·프로필 사진을 **요청하지 않는다**(2026-08-26 §24-2 · 그대로 유지).

⚠️ **「지금 쓰실 수 있다」류의 현재형을 쓰지 않는다** — 그 한 낱말이 이번 모순의 원인이었다.
`test-policies` **14-a** 가 열린 제공자 목록을 `ENABLED_PROVIDERS` 에서 **파생**해 방침·요약과
대조하고, 닫힌 제공자가 「쓸 수 없다」로 적혀 있는지도 함께 잰다.
