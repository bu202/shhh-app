## 2. 실제 코드에서 확인한 현재 자동 가입 흐름

문서가 아니라 `worker/index.js` 를 읽어 확인한 것이다.

```
/login/:provider          → shh_t 쿠키를 심고 SHA-256 을 state 에 서명해 제공자로 보낸다
제공자 동의 화면           → 요청 scope 0개 (구글만 openid)
/cb/:provider             → code 교환 **전에** shh_t 를 대조
exchange()  index.js:465  → 토큰 교환 → /me 호출 → 제공자 회원번호(who) 획득
  index.js:492  const uid = await internalUid(env, name, who);   ← ★ 여기가 곧 가입이다
  index.js:493  return await newSession(env, uid);
```

| 확인한 사실 | 근거 |
|---|---|
| **회원가입 화면·절차가 없다.** 소셜 로그인 성공이 곧 계정 생성이다 | `exchange()` 가 분기 없이 `internalUid()` 를 부른다 (`worker/index.js:492`) |
| `internalUid()` 는 **신규인지 기존인지 호출자에게 알려주지 않는다** | `worker/index.js:511-526` — 두 경우 모두 `id` 문자열 하나만 돌려준다 |
| 신규면 `crypto.randomUUID()` 기반 내부 ID 를 만든다 | 같은 함수. 제공자 번호는 `users` 행 안에서만 산다 |
| 탈퇴 후 같은 제공자 계정으로 재가입하면 **새 내부 ID** 가 생긴다 | 행이 사라졌으므로 첫 `SELECT` 가 비고 새 UUID 를 만든다 |
| 동의·약관·연령을 기록하는 자리가 **어디에도 없다** | `worker/schema.sql` 의 `users` 컬럼은 `id · provider · provider_subject · session_version · created_at` 뿐 |
| 계정 삭제는 한 문장이다 | `worker/index.js:948` `DELETE FROM users WHERE id = ?` + CASCADE |

즉 **사용자가 "가입한다"고 인식할 순간 자체가 화면에 없다.** 이것이 2단계가 다룬 문제의 뿌리다.

## 3. 확정된 회원가입 화면 정책

법률 검토 **전에** 확정되는 항목은 셋뿐이다.

| kind | action | 성격 |
|---|---|---|
| `terms` | `accepted` | 이용약관 **수락** |
| `privacy` | `presented` | 개인정보처리방침 **표시**(고지) |
| `age14` | `attested` | 만 14세 이상 **진술** |

세 가지는 법적으로 서로 다른 행위다. 하나의 "동의"로 뭉치지 않는다 — 고지를 동의로 기록하면
**받지 않은 동의를 받았다고 적는 것**이 된다.

### 승인된 화면 구성

```
┌────────────────────────────────────────────┐
│  shhh! 시작하기                            │
│                                            │
│  ☐ (필수) 이용약관에 동의합니다      [전문] │
│  ☐ (필수) 만 14세 이상입니다               │
│                                            │
│  ── 개인정보처리방침 요약 ──────────────── │
│  · 받는 것: 제공자 회원번호, 단어장,       │
│    직접 지은 별명(선택), 세션              │
│  · 이름·이메일·전화번호·생년월일 안 받음   │
│  · 계정 삭제 시 주 서비스 DB 에서 즉시 삭제 │
│  [개인정보처리방침 전문]                   │
│                                            │
│        [ 가입하기 ]   [ 그만두기 ]         │
└────────────────────────────────────────────┘
```

> **2026-08-17 정정 — 삭제 문구.** 이 상자에 있던 「계정 삭제로 전부 지울 수 있음」은 같은 문서
> §8·§9(Time Travel·백업 복원으로 되살아난다)와 **정면으로 충돌한다.** 화면에 쓸 뜻은 이것이다:
>
> > 계정 삭제 시 주 서비스 DB 에서는 즉시 삭제합니다. 복구 이력의 보유기간과 복원 시 재삭제
> > 절차는 개인정보처리방침에 함께 안내합니다.
>
> 이것도 **최종 법률 문구가 아니다.** 실제 화면·방침 문장은 외부 법률 검토(§6) 뒤에 확정한다.

### 법률 검토 전 **넣지 않는** 것

- ☐ 개인정보 수집·이용에 동의합니다
- `privacy / accepted` 이벤트
- ☐ 국외 이전에 동의합니다 · `xborder` 이벤트
- 전체 동의 체크박스
- 선택 동의를 필수처럼 보이게 하는 UI

이유: 개인정보 보호법 제15조 제1항에서 이 처리의 근거가 **제1호(동의)** 인지 **제4호(계약의 이행)**
인지가 갈리지 않았다. 근거가 계약 이행인데 동의 체크박스를 두면 **철회 가능한 동의처럼 보여**
사용자를 오도하고, 근거가 동의인데 안 두면 근거가 없다. 둘 중 어느 쪽인지는 §6 의 질문이다.

국외 이전도 같다. 제28조의8 제1항 **제1호(별도 동의)** 인지 **제3호(계약 이행을 위한 처리위탁·보관 +
방침 공개)** 인지 확정된 뒤에 설계한다.

## 4. `policy_events` v2 — 설계 승인, **생성은 연기**

### 승인된 설계

```sql
CREATE TABLE policy_events (
  id               INTEGER PRIMARY KEY,
  user_id          TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  kind             TEXT NOT NULL,
  action           TEXT NOT NULL,
  document_version TEXT NOT NULL,
  recorded_at      INTEGER NOT NULL,
  CHECK (
    (kind = 'terms'   AND action = 'accepted') OR
    (kind = 'privacy' AND action = 'presented') OR
    (kind = 'age14'   AND action = 'attested')
  )
);

CREATE INDEX policy_events_user
  ON policy_events(user_id, kind, id DESC);
```

- 복합 `CHECK` 를 쓴 이유: `kind` 와 `action` 을 따로 검사하면 `('age14','accepted')` 같은
  **말이 안 되는 조합이 통과**한다. 셋만 허용해 DB 가 조합 자체를 강제한다.
- `granted`·`withdrawn`·`xborder` 는 스키마에서 **제외**한다. `granted` 는 고지를 동의로 만들고,
  `withdrawn` 은 지금 쓸 자리가 없으며, `xborder` 는 근거가 미확정이다.

### 이번 단계에서 만들지 않는 것

`policy_events` 테이블 · migration 파일 · `worker/schema.sql` 변경 · 가입 API · 가입 UI ·
`scripts/test-policies.mjs`.

### 왜 지금 만들지 않는가 (2026-08-17 시점의 판단 — **2026-08-18 에 해소됐다**)

⚠️ **아래는 당시 사실이다.** 근거가 확정되지 않아 `CHECK` 목록을 정할 수 없었다.
2026-08-18 에 제15조 제1항 제4호로 확정하면서 `migrations/0005` 를 만들었다(§21).

1. ⚠️ 법적 근거가 확정되면 `privacy/accepted` 의 필요 여부가 달라지고, 그러면 **`CHECK` 안의 목록이 바뀐다.**
   (2026-08-18 에 계약 이행으로 확정되면서 이 항목은 `privacy/presented` 하나로 정해졌다.)
2. **SQLite 는 기존 `CHECK` 제약을 `ALTER` 로 바꿀 수 없다.** 바꾸려면 새 테이블을 만들어 옮기고
   옛 테이블을 지우는 재생성 migration 이 필요하다 — `0003` 이 이미 한 번 한 일이다.
3. 따라서 **아직 한 행도 쓰지 않는 테이블에 재생성 migration 을 쓰게 된다.** 이력만 늘고 얻는 것이 없다.

### 남겨 둔 재검토 항목

정책 이벤트를 계정 삭제 후에도 일정 기간 보존해야 한다는 법률 검토 결과가 나오면
`ON DELETE CASCADE` 를 다시 검토해야 한다. **현재 승인된 것은 계정과 함께 지우는 최소 수집 방향뿐**이다.

## 5. `document_version` 무결성 요구사항 (3단계 필수 조건)

`document_version` 은 사람이 손으로 적는 `v1`·`v2` 가 아니라 **사용자가 실제로 본 불변 문서 내용의
SHA-256 해시**다. 손으로 적는 번호는 "사용자가 본 글"과 "우리가 기록한 번호"가 조용히 갈라진다.

| # | 요구사항 |
|---|---|
| 1 | 공개한 약관·방침·연령 문구를 버전별 **불변 파일**로 보존한다 |
| 2 | 기존 버전 파일을 **덮어쓰지 않는다.** 고칠 때는 새 버전 파일을 추가한다 |
| 3 | manifest 가 `종류 · 파일 경로 · SHA-256` 을 잇는다 |
| 4 | 서버는 **manifest 에 등록된 해시만** 기록한다 |
| 5 | 클라이언트는 `document_version` 과 `recorded_at` 을 **지정하지 못한다** |
| 6 | `recorded_at` 은 서버 시각(`Date.now()`)이다 |
| 7 | `scripts/test-policies.mjs` 가 실제 파일 해시와 manifest 를 대조한다 |
| 8 | 내용이 바뀌었는데 manifest 가 그대로면 **테스트가 실패한다** |
| 9 | 계정 생성과 정책 이벤트 기록은 **같은 `batch()`** 로 원자적으로 처리한다 |

이번 단계에서는 요구사항만 확정하고 파일도 테스트도 만들지 않는다.

## 6. 개인정보 처리 근거 · 국외 이전 근거 — 법률 검토 항목

**아래는 질문이지 답이 아니다.** Claude 는 이 중 어느 것도 판정하지 않았다.

| # | 질문 | 왜 갈리는가 |
|---|---|---|
| L1 | 단어장 동기화를 위한 제공자 회원번호·내부 ID·단어 목록 처리의 근거는 개인정보 보호법 **제15조 제1항 제1호(동의)** 인가 **제4호(계약의 이행)** 인가 | 서비스가 "기기 밖 저장"을 제공하기 위해 반드시 필요한 처리라면 제4호일 수 있다. 제4호면 동의 체크박스가 오히려 부정확한 표시가 된다 |
| L2 | L1 이 동의라면, 제22조 제1항의 **구분 동의** 를 어떻게 나누는가 (필수/선택) | 별명은 선택 입력값이다. 선택 동의를 거부해도 서비스를 거부할 수 없다(제22조 제5항) |
| L3 | Cloudflare 를 통한 국외 처리가 제28조의8 제1항 **제1호(별도 동의)** 인가 **제3호(계약 이행에 필요한 처리위탁·보관 + 방침 공개)** 인가 | 제3호면 별도 동의 화면이 필요 없고 방침 공개로 족하다. 제1호면 가입 화면에 항목이 하나 더 는다 |
| L4 | 제3호를 쓸 경우 제28조의8 제2항의 **고지 5항목**(이전 항목·국가·시기와 방법·받는 자·이용 목적과 보유 기간)을 방침에 어떻게 적어야 충분한가 | 현재 `privacy.html` 의 표가 이미 5항목 형태이나 "이전 국가"가 특정되어 있지 않다 (§14 참조) |
| L5 | 계정 삭제 후 정책 이벤트(약관 수락·연령 진술)를 **보존할 근거가 있는가, 보존해야 하는가** | Claude 는 이전 판에서 "계정이 사라지면 보관 근거도 사라진다"고 단정했다. **그것은 법률 판단이었고 철회했다.** 답에 따라 §4 의 CASCADE 가 바뀐다 |
| L6 | 법정대리인 동의 없이 만 14세 미만을 **배제**하는 현재 방식이 제22조의2 상 충분한가. "확인 수단이 없다"는 사실이 사업자 책임을 면하게 하는가 | §7 참조 |
| L7 | 이용약관과 개인정보처리방침을 **가입 시점에 표시**하고 그 시점을 기록하는 것이, 정보통신망법 제50조 등 다른 법령상 요구와 충돌하거나 부족한 부분이 있는가 | 광고성 정보를 보내지 않으므로 제50조는 해당 없다고 보이나 확인이 필요하다 |

**전문가에게 줄 자료**: 이 문서 §2(실제 처리 흐름) · §14(방침과 코드의 차이) · `worker/schema.sql`
(저장 항목 전부) · `privacy.html`.

## 7. 만 14세 이상 정책과 남은 질문

**확정된 것**: 만 14세 이상만 로그인할 수 있다. 로그인 없이 둘러보기는 나이 제한이 없다.
가입 화면에서 `age14 / attested` 로 **진술**을 받는다.

**확정되지 않은 것**:

- 생년월일을 제공자에게 요청하지 않으므로 **나이를 확인할 수단이 전혀 없다.** 이 제한은
  기술적 차단이 아니라 진술이다. `privacy.html:174-176` 이 이 사실을 이미 적고 있다.
- 확인 수단을 만들려면 생년월일이나 본인확인을 받아야 하는데, 그것은 **최소수집 원칙과 정면으로 충돌**한다.
  둘 중 무엇을 택할지는 법률 검토 결과에 달렸다(L6).
- 개인정보 보호법 제22조의2(시행 2023-09-15)는 만 14세 미만에 대해 법정대리인 동의 **및 확인**을
  요구한다. 우리는 만 14세 미만을 받지 않는 설계지만, **받지 않는다는 진술만으로 충분한지**는 미확인이다.

## 8. Time Travel 복원 시 삭제 계정 부활 위협

### 사실

- Cloudflare D1 의 Time Travel 은 **항상 켜져 있고 끌 수 없다.**
- 운영자는 `wrangler d1 time-travel restore` 로 과거 시점을 되살릴 수 있다. **우리가 통제할 수 없는
  기능이 아니다** — 우리가 실행할 수 있는 기능이고, 그래서 우리 절차의 문제다.
- 복원은 **제자리 덮어쓰기**이며 파괴적이다. 다만 실행 결과로 받은 bookmark 로 되돌릴 수 있다.

### 위협

사용자가 계정을 삭제한다 → 며칠 뒤 운영자가 다른 이유로 복원한다 → **삭제된 계정·단어장·별명·
친구 관계·초대 코드가 전부 되살아난다.** 친구 목록에 다시 나타나고 별명이 다시 보인다.

즉 `privacy.html:73` 의 "지우시면 그 자리에서 사라집니다"는 **복원을 하면 거짓이 된다.**

### 검토했다가 **기각한** 대안

| 대안 | 왜 안 되는가 |
|---|---|
| 복원 후 전원 재로그인만 시킨다 | `internalUid()` 가 **살아남은 행을 찾아 돌려준다**(`worker/index.js:511-513`). 재로그인은 탈퇴자를 오히려 원래 계정으로 되돌린다 |
| Time Travel 대신 수동 백업만 쓴다 | 백업 복원도 **똑같이 부활시킨다.** 문제는 복원 수단이 아니라 복원 자체다 |
| 재가입 시 새 무작위 ID 가 생기는 성질에 기댄다 | 그건 **재가입한 사람**만 보호한다. 탈퇴하고 돌아오지 않은 사람은 그대로 부활한다. **보조 보호일 뿐 주 방어책이 아니다** |

## 9. pending / confirmed 삭제 표식 설계 방향 (3단계)

**채택한 방향**: 복원 대상인 주 D1 **밖에** 최소 삭제 표식을 보관하고, 복원 전후에 **확정된** 표식을
재적용한다.

| # | 요구사항 |
|---|---|
| 1 | 주 D1 과 **별도인 저장소**에 전용 삭제 표식을 기록한다 |
| 2 | 원본 제공자 ID · 이메일 · 별명 · 단어장 · 세션을 **저장하지 않는다** |
| 3 | **전용 비밀키로 내부 UID 를 HMAC 한 값만** 저장한다 |
| 4 | `RL_KEY` · `STATE_KEY` · OAuth secret 을 **재사용하지 않는다** — 하나를 교체할 때 다른 하나가 같이 무너진다 |
| 5 | 상태를 `pending` 과 `confirmed` 로 구분한다 |
| 6 | 순서: **pending 기록 → 주 D1 계정 삭제 → 계정 행 부재 확인 → `confirmed_at` 기록** |
| 7 | 주 D1 삭제가 **실패한 pending 표식은 복원 후 삭제에 쓰지 않는다** |
| 8 | 삭제는 성공했는데 `confirmed_at` 기록만 실패한 경우를 되살릴 **reconciliation 절차**를 둔다 |
| 9 | 모든 DB 복원은 **maintenance mode 에서만** 수행한다. ⚠️ **3판 정정: maintenance mode 는 「새 요청의 진입」만 막는다.** 이미 진입한 요청까지 빠져나갔음을 확인하는 **전역 write drain 이 따로 필요하고, 그것이 아직 없어 주 D1 복원은 금지다**(3단계 설계서 §10-8-0·§10-9-6) |
| 10 | 복원 **전에** 현재 주 D1 과 pending 표식을 대조해 삭제 성공 여부를 확정한다 |
| 11 | 복원 **후에** confirmed 표식과 일치하는 부활 계정을 다시 삭제한다 |
| 12 | 재삭제와 CASCADE 결과를 확인한 **뒤에만** 서비스를 재개한다 |
| 13 | **confirmed** 표식은 `max(TIME_TRAVEL_WINDOW, BACKUP_MAX_AGE) + SAFETY_MARGIN` 을 `confirmed_at` 부터 세어 넘긴 뒤 폐기한다. **5판 정정 — 수동 백업도 계정을 되살리므로 Time Travel 만 보면 안 된다.** 현재 계산값 37일은 **미확인 항 둘을 보수적으로 가정한 값이고 확정 보유기간이 아니다.** **pending 표식은 시간으로 폐기하지 않는다** — 설계서 §10-5·§10-5-1 |
| 14 | 플랜이 미확인이므로 **복원 가능 최대 기간**의 안전 기준은 **최대 30일**을 쓴다(표식 보유기간이 아니라 그 산식의 입력값이다). ⚠️ **`privacy.html` 에 「N일 뒤 삭제」를 단정하지 않는다** — 산식의 네 항이 확정되고 법률 검토가 끝난 뒤에 문장을 만든다 |
| 15 | 표식보다 오래된 수동 백업을 남기지 않는다. 폐기할 수 없으면 **restore 금지 대상으로 명시 분류**한다(설계서 §10-5 의 B1·B2 · 법률 `L14`) |

**7번이 왜 있는가**: 표식만 남고 D1 삭제가 실패하면, 사용자는 계정이 살아 있어 계속 쓴다.
그 상태에서 나중에 복원하면 **표식이 살아 있는 계정을 지운다.** `confirmed` 만 재적용하는 규칙이
그 사고를 막는다.

**legacy KV 를 이 저장소로 재사용하지 않는다.** KV 는 §11 에서 폐기하기로 한 자원이고,
지우기로 한 곳에 새 책임을 얹으면 폐기가 영원히 미뤄진다.

이번 단계에서는 별도 DB·KV·테이블·시크릿을 **만들지 않는다.** 설계 요구사항만 확정한다.

## 10. 수동 백업 규칙

| 규칙 |
|---|
| 원격 migration **직전에만** 생성한다. 상시 백업은 금지 |
| 저장소와 Git **밖에** 둔다 |
| 암호화된 로컬 볼륨을 쓴다 |
| 일반 클라우드 동기화 폴더에 평문으로 두지 않는다 |
| 생성 시각 · 목적 · 해시 · **삭제 예정 시각**을 기록한다 |
| 로컬 복원 시험을 수행한다(백업이 실제로 살아나는지) |
| migration 과 smoke test 성공 후 **24시간이 지나면** 삭제한다 |
| 어떠한 경우에도 **7일을 넘겨 보관하지 않는다** |
| 복원할 때는 Time Travel 과 **동일한 삭제 표식 재적용 절차**(§9)를 쓴다 |
| 삭제 표식 보유기간보다 오래된 백업을 만들지 않는다 |

"migration 성공 즉시 삭제"로 하지 않는 이유: 스키마 오류는 즉시 드러나지만 **데이터 오류는 늦게
드러난다.** 24시간은 최소한 하루치 실사용을 관찰할 시간이다. 7일 상한은 그 반대 방향의 제동이다 —
백업은 곧 평문 단어장·별명 사본이라 오래 둘수록 그 자체가 위험이다.

## 11. KV 폐기 6단계 (방향 승인, 이번 단계에서는 삭제하지 않음)

현재 확인된 legacy KV 상태 (**접두사별 개수만** 셈. 2026-08-16 승인된 읽기 전용 조회 →
2026-08-17 Codex 재집계에서 같은 값. **이 문서를 쓰면서 다시 세지는 않았다** — 값이 같았고
KV 는 새 코드가 쓰지 않아 변할 이유가 없다):

| 접두사 | 개수 |
|---|---|
| `b:` | 1 |
| `c:` | 1 |
| `s:` | 2 |
| `u:` | 1 |
| **합계** | **5** |

값과 전체 키 이름은 **확인하지 않았다.** 값 확인은 불필요하다 — 개수만으로 "KV 시대에 계정이 하나
있었다"는 사실이 확인되고, 그것이 판단에 필요한 전부다. `kv key get` · 삭제 · 수정은 하지 않았다.

**확정된 순서**:

| # | 단계 |
|---|---|
| 1 | KV 기반 과거 배포로의 **롤백을 공식적으로 금지**한다 |
| 2 | 현재 D1 세대에서 쓸 수 있는 **배포 롤백 절차**를 확정한다 |
| 3 | 원격 D1 migration 과 현재 코드 세대가 **일치하는지 검증**한다 |
| 4 | `wrangler.jsonc` 의 KV 바인딩과 문서의 KV 의존 설명을 제거한다 |
| 5 | KV 없는 배포를 **별도 승인 후** 실행하고 smoke test 한다 |
| 6 | 사용자의 **파괴적 작업 최종 승인**을 다시 받은 뒤 namespace 를 삭제하고 0개를 확인한다 |

1번이 먼저인 이유: 지금 KV 바인딩이 남아 있는 유일한 근거가 "옛 배포로 롤백하면 그 코드가 KV 를
읽는다"(`wrangler.jsonc:22-24`)이다. 그 근거를 **먼저 명시적으로 폐기하지 않으면** 4번을 할 때
"롤백 경로를 몰래 없앴다"가 된다.

**KV 는 아직 살아 있다. 이번 단계에서 지우지 않았다.**

## 21. 2026-08-18 프로젝트 결정 — §16 착수 조건의 해소

⚠️ **먼저 분명히 한다.** 아래는 **사용자가 공식 자료와 실제 공개 사례를 검토해 내린 프로젝트
운영 결정**이다. **외부 법률 검토 완료가 아니고, 법적 적합성 보증도 아니다.**
법령 변경·사업 확장·유료 결제·민감정보 수집·아동 대상 서비스가 생기면 재검토한다.
현재 이메일·전화번호·생년월일·결제정보·민감정보를 추가 수집하지 않는다.

### 21-1. 확정된 것

| # | 항목 | 결정 | 근거로 채택한 조문 |
|---|---|---|---|
| A | 서비스 제공에 필수인 처리의 근거 | **계약의 이행** | 「개인정보 보호법」 제15조 제1항 **제4호** |
| B | `policy_events` 의 계정 삭제 시 처리 | **ON DELETE CASCADE**(계정과 함께 삭제) | 최소보유 원칙. 탈퇴자 가명키 보존 구조를 만들지 않는다 |
| C | Cloudflare 국외 처리위탁·보관 | **별도 동의를 받지 않는다** | 제28조의8 제1항 **제3호** |
| D | 만 14세 미만 | **가입 대상에서 제외.** 법정대리인 동의 절차를 만들지 않는다 | 필수 진술 1개. 본인확인은 하지 않는다 |
| E | 외부 법률 검토(L1~L15) | **4단계 착수 게이트에서 제외.** 공개 출시 조건에는 남는다 | — |

### 21-2. 그래서 §16 의 다섯 조건이 이렇게 됐다

| # | §16 의 조건 | 지금 |

| 1 | 개인정보 처리의 법적 근거 확정 (L1·L2) | ✅ 프로젝트 결정 A |

| 항목 | 상태 |
|---|---|
| 국외 처리의 **실제 국가 특정** | ⚠️ **못 했다.** Cloudflare 는 위치를 국가가 아니라 지역으로 알려준다. 우리 D1 은 `running_in_region: APAC` · `jurisdiction: null` 이다(2026-08-18 읽기 전용 확인). **APAC 은 국가도 관할권도 아니다.** `privacy.html` 에 확인한 것과 확인 못 한 것을 나눠 적었다 |
| 복구본·삭제 표식의 **보유기간** | ⚠️ **못 정했다.** 요금제의 Time Travel 기간과 수동 백업 규칙이 미확정이다. 코드의 37일은 **기술적 보수 계산값**(`CONFIRMED_RETENTION`)이고 방침에는 숫자를 적지 않았다 |

| 외부 법률 검토 | ⚠️ 미완료. **공개 출시 No-Go 조건에 그대로 남는다**(§17 의 1번) |

### 21-4. `privacy.html` 불일치 — §14 의 처리 결과

| # | §14 항목 | 처리 |
|---|---|---|
| 1 | 둘러보기가 「아무 정보도 수집하지 않는다」 | ✅ 「로그인하지 않아도 남는 것」 절을 새로 만들어 호스팅 접속 기록·국립국어원 요청·리미터 변환값 셋을 적었다 |

### 21-5. 이 결정이 바꾸지 **않은** 것

- **공개 OAuth·계정 출시는 여전히 No-Go 다**(§17). 바뀐 것은 「4단계 구현을 시작해도 되는가」뿐이다.
- **주 D1 복원 금지**는 그대로다. 근거는 법률이 아니라 기술이다(설계서 §10-8-0).
- `docs/PRIVACY_LEGAL_REVIEW_PACKET.md` 는 **삭제하지 않는다.** 외부 검토를 받게 되는 날
  그대로 전달할 자료이고, L1~L15 는 여전히 답이 필요한 질문이다.
