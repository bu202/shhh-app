## 1. 결정 ㉫ — 웹과 앱이 **같은 출입증**을 쓴다 (2026-09-05 사용자 결정)

| 기호 | 무엇 | 정한 값 |
|---|---|---|
| ㉫ | 웹과 네이티브가 **세션을 어떻게 나르나** | **지금의 쿠키 하나로 통일한다.** 앱은 자기 쿠키 저장소를 갖고, OAuth 콜백 뒤 **`/api/exchange/:provider`** 를 불러 자기 세션 쿠키를 받는다. ⛔ **앱 전용 Bearer 토큰 경로를 만들지 않는다** |

**왜** — ⛔ **인증 경로가 둘이 되면 방어도 두 벌이 되고, 두 벌은 반드시 한쪽만 낡는다.**
이 저장소가 그 무늬로 이미 두 번 다쳤다: **위협 79**(정지가 batch 안에서 반만 적용돼 화면은
「정지됨」인데 친구에게는 그대로 보였다) · **위협 80**(옛 클라이언트 차단이 화면에만 있고 서버에
없었다). 세대 무효화(`session_version`)·정지·재개·삭제·행위자 술어(`worker/fence.js`)가
**전부 세션 하나를 전제로 짜여 있다.**

### ⛔ 정정 — **다리는 아직 없다** (2026-09-05 Codex 독립 검토 11 · **P0 2건** · 코드로 재현 확인)

⛔ **이 문서 첫 판은 「다리는 이미 있다」고 적었다. 틀렸다.** `/api/exchange/:provider` 는
**같은 브라우저 안의 PWA 화면**을 위한 자리이지 **네이티브 앱을 위한 자리가 아니다.**
⚠️ **사용자에게 ㉫ 를 물을 때 이 문장을 근거로 제시했다** — 그래서 ㉫ 가 실제보다 싸 보였다.

**막는 것 둘 — 코드에서 직접 확인했다:**

1. **거래 표(`shh_t`)가 인증 브라우저에만 있다.** `/api/login/:provider` 가 심는 `HttpOnly`
   쿠키이고, `/exchange` 는 `bound(env, req, st)` 로 그 표와 OAuth state 를 대조해 **어긋나면
   제공자 호출 전에 400** 이다(`worker/index.js` · 「이 기기에서 시작한 로그인이 아니에요」).
   ⚠️ **앱의 인증 창(iOS `ASWebAuthenticationSession` · Android Custom Tabs)은 앱과 쿠키
   공간이 다르다** — 앱이 `/exchange` 를 직접 부르면 **표가 없어서 400** 이다.
   ✅ **이 방어는 옳다** — 남의 code/state 링크를 받은 사람이 로그인되는 것을 막는다(위협 그대로).
   ⛔ **그러니 이 검사를 없애서 푸는 것이 아니다.**
2. **비-GET 요청은 `Origin` 이 없으면 403 이다.** 「없는 것도 막는다」가 **의도된 규칙**이고
   (`worker/index.js` CSRF 절), `test-friends` 가 `PUT /me/book`·`DELETE /me/session`·
   `POST /friends` 의 무-Origin 요청 거부를 고정한다. **네이티브 HTTP 클라이언트는 `Origin` 을
   붙이지 않는다.** ⚠️ **앱이 웹 Origin 문자열을 스스로 넣으면 통과하지만 그것은 앱이 주장한
   문자열일 뿐이라 브라우저의 Origin 과 같은 보증이 아니다.**
   ⚠️ **`SameSite=Lax` 도 브라우저 쿠키의 규칙이지 네이티브 클라이언트의 인증 수단이 아니다.**

⛔ **이 둘은 APP-1 로 미룰 것이 아니라 PWA-3 이 설계할 것이다**(첫 판은 「실측 전까지 단정하지
않는다」며 미뤘다 — 미룰 수 있는 성질이 아니다). **§3 의 결정 대기 1·2 가 그것이다.**

✅ **㉫ 의 결론이 무효가 된 것은 아니다** — 「인증 경로를 둘로 만들지 않는다」는 성립한다.
⛔ **다만 「공짜로 된다」가 아니라 「다리를 새로 설계해야 한다」로 값이 바뀌었다.**
⚠️ **그래서 사용자에게 다시 확인받는다**(2026-09-05).

⚠️ **감수하기로 한 것**(2026-09-05 사용자에게 고지하고 고름):
- 앱이 **쿠키 저장소를 직접 관리**해야 한다. 저장소가 초기화되면 로그아웃된다.
- iOS `ASWebAuthenticationSession` / Android Custom Tabs 가 **앱과 다른 쿠키 공간**이라,
  거기서 돌아온 뒤 **앱이 스스로 `/exchange` 를 부르는 다리**를 정확히 놔야 한다.
  ⛔ **틀리면 오류 없이 「로그인이 안 되는」 상태가 된다** — 그래서 이 다리에 테스트를 붙인다(§6).
- ⛔ **그 가능성이 얼마인지는 모른다** — 확률로 적지 않는다.

⛔ **다른 앱 사례를 근거로 적지 않았다**(2026-09-05). 카카오·당근이 **자기 서버 세션**을 앱에
어떻게 주는지는 **공개돼 있지 않다.** 공개된 것은 제공자 SDK 가 앱에 주는 토큰이고 **그것은 다른
층**이다. ⚠️ **확인하지 못한 것을 사례로 쓰지 않는다.**

### 1-1. ㉫ 가 정하지 **않는** 것

- ⛔ **쿠키 속성을 바꾸지 않는다** — `HttpOnly; Secure; SameSite=Lax; Path=/api` 그대로다.
- ⛔ **`SESSION_DAYS`(90)를 건드리지 않는다** — 그 값의 원본은 코드 상수 하나이고
  `test-policies` 13-a 가 방침 문장과 대조한다.
- ⚠️ **네이티브가 `SameSite=Lax` 의 보호를 그대로 받는지는 아직 확인하지 않았다** —
  그것은 **브라우저의 성질**이고 앱의 HTTP 클라이언트에는 그 개념이 없다.
  ✅ **그래서 서버 쪽 Origin 검사가 그대로 남는다**(`worker/index.js` 의 same-origin 검사) —
  ⛔ **「SameSite 가 막아 주니까」를 근거로 서버 검사를 빼지 않는다.**
  ⛔ **앱 요청의 Origin 이 무엇이 되는지는 실측 전까지 단정하지 않는다**(APP-1 에서 잰다).

### 2-1. ⛔ 재가입은 막히지 않는다 — 설계된 결과다

DI 의 HMAC 은 **탈퇴 즉시 지운다**(§29-2). 그래서 **탈퇴한 사람은 곧바로 다시 가입할 수 있고
새 내부 ID 를 받는다.** ⚠️ **이것은 빠뜨린 것이 아니라 ㉠ 과 맞는 결과다** — ㉠ 이 막는 것은
**「한 사람이 여러 계정으로 *동시에* 여러 명과 관계 맺는 것」**이고, 탈퇴 뒤 재가입은 동시가 아니다.
⛔ **부정이용 방지를 위해 탈퇴 후 DI 를 보관하지 않는다** — **탈퇴자를 다시 식별하는 데 쓸
데이터를 남기지 않기로 했기 때문**이다(2026-08-26 사례 비교표 · 결정 B 의 CASCADE 와 같은 방향).
⛔ **당시 사실 — 이 문서 첫 판:** 이 자리는 **「그 목적의 데이터가 우리에게 없다」**였다.
**그것은 틀렸다**(2026-09-05 Codex 독립 검토 11 · P2) — `privacy.html` 은 **남용 방어용 변환값과
횟수**를 저장한다고 적고, 새 모델에는 **2년짜리 관리자 열람 감사기록**(㉨)도 있다.
⚠️ **없는 것은 「부정이용 방지 데이터」가 아니라 「탈퇴자를 다시 잇는 식별자」다.**
⚠️ **실제 서비스 중에는 그 목적으로 탈퇴 후에도 DI 를 보관하는 곳이 있다** — 우리와 목적이 다르다.

## 3. 남은 결정 — ⛔ 정해지기 전에는 그 부분을 구현하지 않는다

⛔ **첫 판의 다섯 중 둘은 이미 정해져 있던 것을 내가 다시 연 것이었다**(2026-09-05 Codex 독립
검토 11 · P1·P2). **이 저장소에서 가장 비싼 실수라 그대로 적어 둔다** — 아래 「⛔ 다시 열지
않는다」가 그것이다.

1. **인증 창에서 앱으로 세션을 어떻게 넘기나**(㉫ 의 다리 · **P0**). 거래 표(`shh_t`)가 인증
   브라우저에만 있어서 앱이 `/exchange` 를 직접 못 부른다. ⛔ **표 대조를 없애는 답은 안 된다** —
   그것이 막는 공격이 실재한다. ⚠️ **Claude 가 방식을 고르지 않는다** — 선택지를 만들어 묻는다.
2. **네이티브의 상태 변경 요청을 무엇으로 지키나**(**P0**). 지금은 `Origin` 없으면 403 이고
   그것이 의도된 규칙이다. ⚠️ **앱이 Origin 문자열을 스스로 넣는 것은 브라우저 Origin 과 같은
   보증이 아니다.** ⛔ **「앱이니까 통과」로 열지 않는다.**
3. **본인확인 실패·중단 시 무엇을 남기나.** ㉦ 은 **만 14세 미만 차단**만 정했다(아무것도 안 남긴다).
   ⚠️ 본인 아님·시간 초과·취소·기관 장애는 정해진 것이 없다. 리미터가 필요하다는 것만 정해져 있다.
4. **정보 수정의 범위 — 생년월일 오기 정정.** 새로 저장하는 값인데 규칙이 없다.
   ⚠️ 현재 방침의 「별명·단어장만」은 **생년월일을 안 받던 때의 문장**이다.
5. **새 스키마에서 탈퇴가 무엇을 지우고 무엇을 남기나.** 감사기록은 **2년**(㉨), DI·생년월일은
   **탈퇴 즉시**. 그 사이의 **연결 끊기·가명화·트랜잭션 경계**가 없다.
6. **기관이 바뀌어 DI 가 어긋날 때 기존 회원을 어떻게 하나.** §29-4 가 **PWA-3 으로 명시 이연**했다.
   ⚠️ HMAC 버전에 기관을 적는 것은 **조용한 실패를 시끄러운 실패로 바꿀 뿐** 차단을 지켜 주지 않는다.
7. **별명 금칙어 목록의 출처.** 정규화·중복 검사는 정해졌고 **목록을 어디서 가져오나**가 없다.
8. **제공자별 연결 해제 API 가 실제로 있는가, 실패하면 탈퇴를 막는가.**
   ⛔ **「해제할 것인가」는 열려 있지 않다** — 아래를 볼 것.
