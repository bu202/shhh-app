# 개인정보 법률 검토 전달 자료 — shhh!

**작성 2026-08-17 · 개정 2026-08-17(5판) · 이 문서는 사실 자료다. 법률 결론이 없다.**

**5판에서 바뀐 것** — ① **L13·L14·L15 추가**(제공자 식별자 성질 · 백업과 표식 보유기간의 동기화
· 가입 정보의 제공자 URL 통과) ② 「제공자 회원번호는 서비스 전용 값」이라는 **근거 없는 단정 삭제**
(§2-3 신설) ③ 「OAuth 가 수행된 적 없다」는 **단정 삭제** — 현재 비활성 / 현재 0명 / 과거 KV 시절
**배제 불가**를 갈라 적음 ④ 보유기간 산식을 **`max(Time Travel, 수동 백업) + 안전 여유`** 로 정정
(수동 백업도 계정을 되살린다) ⑤ **37일을 확정 보유기간·방침 문구로 쓰지 않는다**고 명시.

이 문서는 외부 전문가(변호사·개인정보 전문가)에게 그대로 전달하기 위한 것이다.
**AI 가 작성했으며 법률 판단은 하나도 포함하지 않는다.** 질문은 §12 에 모아 두었다.

### 지금 무엇이 공개되어 있고 무엇이 아닌가 (4판 정정)

3판까지 "서비스는 아직 공개되지 않았다"고 적었다. **정확하지 않다.** 웹 주소는 인터넷에서
열린다. 정확히는 아래와 같다.

| 대상 | 상태 |
|---|---|
| **웹/PWA 의 정적 기능**(사전 검색·수형 보기·연습) | **인터넷에서 접근 가능하다.** `https://shhh-app.pages.dev/` · 로그인 없이 전부 쓸 수 있다 |
| **공개 OAuth·계정 기능**(로그인·단어장 동기화·친구) | **비활성.** 제공자 시크릿을 넣지 않아 로그인이 완료되지 않는다 |
| **앱스토어 출시** | **미출시** |
| 실사용자 | **0명**(원격 DB `SELECT COUNT(*) FROM users` = 0, 2026-08-17 실측) |

즉 **개인정보를 처리하는 기능만 꺼져 있고, 그 밖의 서비스는 이미 열려 있다.**

### 아래 처리 흐름 중 무엇이 코드이고 무엇이 설계인가 (4판 정정)

3판까지 "아래 처리 흐름은 코드에 구현되어 있으나"라고 적었다. **예정된 설계까지 구현된 것처럼
읽힌다.** 갈라서 적는다.

| 구분 | 항목 |
|---|---|
| **코드에 실제로 존재한다** | 소셜 로그인·세션 · 단어장 저장·동기화 · 친구 관계·초대 코드 · 계정 삭제(`DELETE FROM users` + 연쇄 삭제) |
| **설계만 있고 코드가 없다** | **회원가입 화면**(약관 수락·연령 진술) · **`policy_events`**(정책 기록 표) · **삭제 표식 ledger** · **가입 state 소비 표식** · **유지보수 모드** · **전역 write drain** |

검토 결과에 따라 **출시 전에 설계를 바꿀 수 있다** — 그것이 지금 검토를 요청하는 이유다.
**아직 코드가 없다는 것이 바꾸기 쉬운 이유이기도 하다.**

#### ⚠️ 「OAuth 로그인이 수행된 적 없다」고 적지 않는다 (4판 정정)

3판까지 위 표에 "OAuth 비활성이라 **수행된 적 없음**"이라고 적었다. **그렇게 단정할 근거가 없다.**
세 가지 사실을 갈라 적는다.

| 사실 | 상태 | 근거 |
|---|---|---|
| **현재** 공개 OAuth 는 비활성이다 | **확인됨** | 제공자 시크릿 미등록. `/api/ready` 의 `providers` 가 비어 있다 |
| **현재** 주 D1 의 사용자는 0명이다 | **확인됨** | 원격 `SELECT COUNT(*) FROM users` = 0 (2026-08-17 실측) |
| **과거** KV 저장소 시절에 OAuth 로그인이 수행된 적이 있는가 | **배제할 수 없다** | legacy KV 에 `u:`1 · `s:`2 · `b:`1 · `c:`1 = 5개 값이 **남아 있다**(§7). 개발자 본인 계정으로 **보이지만** 값과 전체 키 이름을 확인하지 않았다. 현재 비활성이라는 사실은 **과거에 대해 아무것도 말해 주지 않는다** |

즉 「지금 개인정보 처리가 일어나지 않는다」는 말할 수 있지만, 「이 서비스가 개인정보를 처리한
적이 한 번도 없다」는 **말할 수 없다.** 검토 시 이 구분을 전제로 보아 주시기 바란다.

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 이름 | shhh! |
| 무엇 | 한국어 단어에 대응하는 **한국수어(KSL) 단어**를 보여주고, 사용자가 외우고 싶은 단어를 「우리 단어장」에 담아 연습하는 학습용 웹앱(PWA) |
| 데이터 출처 | 국립국어원 한국수어사전(`sldict.korean.go.kr`)의 공개 자료 |
| 사업 형태 | 개인 개발자. 법인 아님. **결제·광고·마케팅 전송 없음** |
| 현재 상태 | 앱스토어 **미출시**. 웹/PWA 의 정적 기능은 **인터넷에서 접근 가능**. 공개 OAuth·계정 기능은 **비활성** |

## 2. 현재 수집·저장하는 값 (전부)

DB 스키마(`worker/schema.sql`)에 있는 것이 전부다. 아래에 없는 값은 저장하지 않는다.

| # | 항목 | 어디서 오나 | 저장 위치 | 비고 |
|---|---|---|---|---|
| 1 | **제공자 회원 고유번호** | 카카오·네이버·구글이 주는 식별 번호 | `users.provider_subject` | **응답·화면·친구 목록 어디에도 나가지 않는다.** ⚠️ 다른 서비스와 대조 가능한 값인지는 **제공자마다 다르고, 셋 다 확정하지 못했다 — 아래 §2-3** |
| 2 | **제공자 이름** | 셋 중 하나 | `users.provider` | `kakao`/`naver`/`google` |
| 3 | **내부 무작위 계정 번호** | 서비스가 생성(UUID) | `users.id` | 밖으로 나가는 유일한 식별자. 친구에게 보이는 값이 이것이다 |
| 4 | **단어장 단어 목록** | 사용자가 담은 한국수어 단어 | `books.words` (JSON 배열) | 최대 500단어·단어당 100자 |
| 5 | **별명** (선택) | **사용자가 직접 입력**. 제공자에게서 가져오지 않는다 | `books.nickname` | 최대 20자. 아무 말이나 가능. 비우면 삭제 |
| 6 | **세션 토큰의 해시** | 로그인 시 생성 | `sessions.token_hash` | 원본은 저장하지 않는다. 브라우저의 HttpOnly 쿠키에만 있다 |
| 7 | **친구 관계** | 초대 링크를 주고받은 결과 | `friendships` | 두 사람의 **내부 번호** 한 쌍 + 상태(요청/수락) |
| 8 | **초대 코드** | 서비스가 생성(무작위 12자) | `invite_codes.code` | 사람당 활성 1개 |
| 9 | **남용 방지 카운터** | 요청이 올 때 | `rate_limits.bucket`, `n` | **아래 §3 참조** |

### 2-1. 남용 방지 카운터의 성질 (항목 9)

- 목적: 초대 코드 무차별 대입과 로그인 반복 시도를 막는 것.
- 저장하는 값: `HMAC-SHA256(비밀키, "용도|주체|분단위 창번호")` 와 **횟수**.
  - 「주체」는 로그인한 사람이면 내부 번호, 아니면 **IP 주소**다.
  - **IP 주소나 계정 번호 원문은 저장하지 않는다.**
  - 비밀키를 모르면 이 값에서 원래 IP 를 되찾을 수 없다(키 없는 단순 해시는 IPv4 전수 대입으로
    복원 가능했고, 실측 확인 후 2026-08-16 에 비밀키 방식으로 바꿨다).
- 수명: 1분 창. 지난 행은 **다음 로그인이 일어날 때** 삭제된다.
  - ⚠️ **독립적으로 주기 실행되는 정리 수단이 없다.** 지우는 코드가 로그인 경로에만 붙어 있어(`worker/index.js:256-261`)
    아무도 로그인하지 않으면 만료된 행이 계속 남는다. **2026-08-18 09:20 KST 원격 실측: 5행 전부
    만료 상태로 남아 있다**(가장 늦은 만료도 2026-08-17). 이것은 설계상 예외가 아니라 현재 구현의
    한계이며, 정리 전용 작업(설계서 §10-5-2)은 아직 만들지 않았다.

### 2-2. 로그인하지 않은 사용자

**앱을 정상적으로 쓰는 동안에는** 서비스 서버에 저장되는 값이 없다. 앱이 보내는 요청은
`/api/health` 하나뿐이고 그 요청은 아무것도 저장하지 않는다.

> ⚠️ **5판 정정 — 「없다」고 단정하지 않는다.** 4판까지 "서비스 서버에 저장되는 값이 **없다**"고
> 적었다. **한 가지 경로에서 사실이 아니다.**
>
> | 사실 | 내용 |
> |---|---|
> | 어떤 경로 | 로그인 콜백 주소(`/api/cb/…`)를 **직접 여는 경우.** 앱은 이 주소를 스스로 부르지 않지만, 주소를 아는 사람이면 누구나 열 수 있다 |
> | 무슨 일이 나나 | 남용 방지 카운터가 **제공자 확인보다 먼저** 돈다(`worker/index.js:787`). 로그인하지 않은 요청이라 **주체가 IP 주소**가 되고, 그 IP 로 만든 요약값 한 줄이 `rate_limits` 에 **저장된다** |
> | 저장되는 값 | `HMAC-SHA256(비밀키, "login\|IP\|분단위 창번호")` 와 횟수. **IP 원문은 저장되지 않는다**(§2-1) |
> | 수명 | 1분 창. 다만 실제 삭제는 **다음 로그인이 일어날 때**다 — 아무도 로그인하지 않으면 남는다 |
> | **지금 실제로 일어난다** | 비밀키(`RL_KEY`)가 **production 에 등록되어 있다**(2026-08-17). 카운터는 **실제로 돈다** — 같은 날 라이브 실측에서 로그인하지 않은 요청 12회에 한도가 걸렸다 |
> | 라이브 `/api/ready` 가 503 인 이유 | **`providers: []`**, 즉 OAuth 제공자가 설정되지 않았기 때문이다. `RL_KEY` 부재도 DB 오류도 **아니다** — 같은 응답의 `db:true` 가 DB 접근을 증명하고, 시크릿 이름 목록에 `RL_KEY` 가 있다(2026-08-18 재측정) |
>
> 즉 **「로그인하지 않으면 아무것도 저장되지 않는다」는 이미 사실이 아니다.** 저장되는 것은
> 키 없이는 되돌릴 수 없는 요약값 하나뿐이지만, **없다고 적는 것과 있다고 적는 것은 다르다.**
> `privacy.html` 의 「남용을 막기 위한 처리」 절이 이 처리를 이미 설명하고 있으나,
> **「로그인하지 않은 사용자」 절과 나란히 읽으면 서로 다른 말로 읽힌다** — §10 의 불일치 목록에 추가했다.

- 다음 네트워크 요청이 발생하며 **호스팅 사업자에게 접속 기록(IP·시각 등)이 남을 수 있다**:
  - 앱 자체를 내려받는 요청 (Cloudflare Pages)
  - 수형 그림을 받기 위한 `sldict.korean.go.kr` 요청 (국립국어원)
  - `/api/health` 요청 1회 — "어느 방식으로 로그인할 수 있나"만 묻고, **사용자를 가리키는 값이
    아무것도 실리지 않는다**
- 검색어·단어장 내용은 어느 요청에도 실리지 않는다.

### 2-3. 제공자 회원 고유번호의 성질 — **제공자별로 갈라 적는다** (4판 신설)

3판까지 이 값을 "**이 서비스 전용 값**이라 다른 서비스에서 같은 사람을 찾는 데 쓸 수 없다"고
한 줄로 적었다. **셋을 하나로 일반화한 것이고 근거를 확인하지 않았다.** 같은 문장이
`worker/index.js` 주석에도 있었고 함께 정정했다.

이 값이 **서비스마다 다른 값(pairwise)** 인지 **모든 서비스에 같은 값(public)** 인지는
「다른 서비스의 기록과 대조해 같은 사람을 특정할 수 있는가」를 가르므로 **가명·식별 가능성 판단의
전제**가 된다. 확인 결과는 다음과 같다.

| 제공자 | 저장 값 | 공식 문서에서 확인한 것 | 판정 |
|---|---|---|---|
| **구글** | `sub` (OpenID Connect) | "An identifier for the user, **unique among all Google Accounts and never reused**." · "A Google Account can have multiple email addresses at different points in time, but the `sub` value is never changed." — **클라이언트별로 값이 갈린다는 서술은 없다** | ⚠️ **서비스 전용이라고 볼 근거가 없다.** 오히려 계정 단위 전역 식별자로 읽힌다 |
| **카카오** | 회원번호 `id` | **확인하지 못했다.** 공식 문서(`developers.kakao.com`)에 접근하지 못했다 | **확인 필요** |
| **네이버** | 회원 식별자 `id` | **확인하지 못했다.** 공식 문서(`developers.naver.com`)에 접근하지 못했다. 비공식 자료는 「애플리케이션별 고유값」이라고 하나 **공식 근거가 아니다** | **확인 필요** |

확인 일자: **2026-08-17**. 확인 수단: 공식 문서 직접 조회(구글만 성공).

> **그래서 이 자료는 「대조 불가능하다」에 기대지 않는다.** 우리가 사실로 말할 수 있는 것은
> **이 값이 서비스 밖으로 나가지 않는다**는 것 하나뿐이다(응답·화면·친구 목록·로그 어디에도
> 실리지 않는다 — `worker/index.js` 의 `internalUid` 가 내부 무작위 번호로 바꾼다).
> 대조 가능성 자체는 **미확정**이며, 이것이 아래 **L13** 의 질문이다.

## 3. 수집하지 않는 값

OAuth 동의항목(scope)을 **0개**로 요청한다(구글만 `openid`, 이는 식별자 `sub` 만 받는 최소 범위).

- 이름 · 이메일 · 전화번호 · **생년월일** · 프로필 사진 · 성별
- 위치 · 연락처 · 사진 · 통화·문자 기록
- 광고 식별자 · 분석/추적 도구 (Google Analytics 등을 쓰지 않는다)
- 검색어 (사전에서 무엇을 찾았는지는 어디에도 전송하지 않는다)
- 제공자의 친구 목록

## 4. 이용 목적

| 항목 | 목적 |
|---|---|
| 제공자 회원 고유번호 · 내부 번호 | 같은 사람의 단어장을 기기가 바뀌어도 이어 주기 위한 **계정 식별** |

| 별명 | 친구 목록에서 누가 보낸 요청인지 구분 |

## 6. 보유기간과 삭제

| 항목 | 보유 |
|---|---|
| 단어장·별명·친구 관계·초대 코드·계정 번호 매핑 | **계정을 삭제할 때까지** (기간 정함 없음) |
| 세션 | 발급으로부터 180일. 만료된 행은 **다음 로그인이 일어날 때** 삭제 |
| 남용 방지 카운터 | 1분 창. 다음 로그인 때 정리 |
| 법령상 별도 보관 의무 | **확인하지 못했다.** 결제·거래 기능이 없다는 것이 우리가 아는 사실이고, **그런 서비스에 별도 보관 의무가 존재하는지는 판단하지 않았다** — L7 의 외부 검토 대상이다 |

### 6-1. 삭제 흐름

- 사용자가 앱 안에서 직접 삭제한다: **마이 → 설정 → 계정 → 계정 삭제**.
- 서버는 `DELETE FROM users WHERE id = ?` **한 문장**을 실행하고, 외래키 CASCADE 로
  세션·단어장·친구 관계·초대 코드가 **함께** 삭제된다. 중간 상태가 존재할 수 없다.
- 삭제 즉시 **모든 기기에서 로그인이 풀린다.**
- 문의 주소를 통한 삭제 요청도 안내하고 있다.

### 6-2. **삭제 후 데이터가 되살아날 수 있는 경로 — 중요**

이 항목은 검토에서 반드시 다뤄져야 한다고 보고 자료에 포함했다.

| 경로 | 사실 |
|---|---|
| **Cloudflare D1 Time Travel** | D1 에 **항상 켜져 있고 끌 수 없는** 시점 복원 기능이다. 운영자가 `restore` 를 실행하면 과거 시점으로 **제자리 덮어쓰기** 된다. 복원 가능 기간은 플랜에 따라 7일(무료) 또는 30일(유료)이며 **현재 플랜은 미확인**이라 안전 기준으로 30일을 쓰고 있다 |
| **수동 백업** | 원격 DB 변경(migration) 직전에만 생성하는 규칙이다. 저장소·Git 밖, 암호화 볼륨, 24시간 뒤 삭제, 7일 상한 |
| **되살아나는 것** | 복원하면 삭제된 계정·단어장·별명·친구 관계·초대 코드가 **전부 돌아온다.** 그 사람이 다른 사용자의 친구 목록에 다시 나타나고 별명이 다시 보인다 |
| **현재 상태** | 복원 시 삭제를 재적용하는 절차를 **설계했으나 구현하지 않았다.** 그래서 현재 규칙은 **「복원 금지」** 다 |
| 계획 중인 대응 | 주 DB **밖**의 별도 저장소에 삭제 표식을 남기고, 복원 전후에 확정된 표식을 재적용해 다시 삭제한다. 표식은 **내부 계정 번호를 전용 비밀키로 HMAC 한 값 하나**이며 제공자 ID·이메일·별명·단어장을 저장하지 않는다. 복원은 **모든 쓰기가 중단되고 이미 진입한 요청까지 빠져나간 것이 확인된 상태**에서만 수행하고, 재삭제 결과(삭제된 행 수·잔여 데이터 0건)를 확인한 뒤에만 서비스를 재개한다. ⚠️ **그 「빠져나간 것을 확인하는 수단」이 아직 구현되지 않았고, 그래서 위 「현재 상태」의 복원 금지가 유지된다** |
| 표식의 보유기간(계획) | **상태에 따라 다르다.** ① **confirmed**(삭제 확정): `확정 시각 + 되살릴 수 있는 모든 경로의 최대 나이 + 안전 여유 7일`. ② **pending**(성공 여부 미확인): **자동 삭제하지 않는다** — 사람이 판정할 때까지 남는다. **숫자는 아직 확정하지 않았다** — 산식과 미확정 항목은 §12-2(L9-1~L9-6 · **L14**) |
| **표식의 성질** | **익명정보라고 보지 않는다.** 복원된 DB 의 계정 번호들과 대조하면 특정 개인을 가려낼 수 있으므로 **가명·최소 식별값**으로 취급한다. (이 취급이 적정한지도 검토 대상, §12 L9) |

## 9. 도입 예정인 회원가입 화면과 기록 (아직 구현 없음)

**현재는 회원가입 절차가 없다. 소셜 로그인 성공이 곧 계정 생성이다.**
사용자가 "가입한다"고 인식할 순간이 화면에 존재하지 않는다. 이를 고치려는 것이 이번 설계다.

### 9-1. 가입 화면 (설계안)

```
shhh! 시작하기

☐ (필수) 이용약관에 동의합니다              [전문]
☐ (필수) 만 14세 이상입니다

── 개인정보처리방침 요약 ──────────────
· 받는 것: 제공자 회원번호, 단어장, 직접 지은 별명(선택), 세션
· 이름·이메일·전화번호·생년월일 안 받음
· 계정 삭제 시 주 서비스 DB 에서 즉시 삭제
[개인정보처리방침 전문]

        [ 가입하기 ]   [ 그만두기 ]
```

**법률 검토 전이라 일부러 넣지 않은 것**: 「개인정보 수집·이용에 동의합니다」 체크박스,
「국외 이전에 동의합니다」 체크박스, 「전체 동의」 체크박스.
이유는 §12 의 L1·L3 이 확정되지 않았기 때문이다 — 처리 근거가 계약 이행인데 동의 체크박스를 두면
철회 가능한 동의처럼 보여 사용자를 오도하고, 근거가 동의인데 안 두면 근거가 없다.

### 9-2. 기록 예정 스키마 (`policy_events`) — 두 분기

기록되는 값은 **행위의 종류 · 문서의 내용 해시 · 서버 시각**뿐이다.
IP · User-Agent · 위치 · 시각 외 접속 정보는 기록하지 않는다.

```sql
CREATE TABLE policy_events (
  id               INTEGER PRIMARY KEY,
  user_id          TEXT NOT NULL,          -- 내부 무작위 번호
  kind             TEXT NOT NULL,          -- terms | privacy | age14 (| xborder)
  action           TEXT NOT NULL,          -- accepted | presented | attested
  document_version TEXT NOT NULL,          -- 사용자가 실제로 본 불변 문서의 SHA-256
  occurred_at      INTEGER NOT NULL,       -- 체크하고 가입 버튼을 누른 시각 (§12-1 의 ①)
  recorded_at      INTEGER NOT NULL        -- DB 에 기록된 시각 (③)
);
-- 두 시각 모두 **서비스 서버의 시각**이며 클라이언트가 지정할 수 없다.
```

| 분기 | 허용 조합 |
|---|---|
| **①** 처리 근거가 **계약의 이행**인 경우 | `terms/accepted` · `privacy/**presented**`(고지) · `age14/attested` |
| **②** 처리 근거가 **동의**인 경우 | `terms/accepted` · `privacy/**accepted**` · `age14/attested` (+ 국외 이전이 별도 동의 대상이면 `xborder/accepted`) |

- 고지(`presented`)와 동의(`accepted`)를 **같은 값으로 기록하지 않는다.** 법적으로 다른 행위이며,
  고지를 동의로 적으면 받지 않은 동의를 받았다고 기록하는 것이 된다.
- `document_version` 은 사람이 붙이는 `v1`·`v2` 가 아니라 **사용자가 실제로 본 불변 문서의 내용
  해시**다. 버전별 문서 파일을 불변으로 보존하며 덮어쓰지 않는다.

## 10. 현재 개인정보처리방침과 코드의 알려진 불일치 8건

**아직 고치지 않았다.** 법적 근거가 확정되어야 어떤 문장으로 고칠지가 정해지기 때문이다.
검토자가 현재 방침을 읽을 때 참고하시라고 그대로 적는다.

| # | 방침의 서술 | 실제 |
|---|---|---|
| 1 | 로그인 없이 둘러보기는 "아무 정보도 수집하지 않기 때문"에 나이 제한이 없다 | 로그인하지 않아도 국립국어원 이미지 요청과 `/api/health` 요청이 나가고 **호스팅 사업자에게 IP 가 남는다.** 같은 문서의 다른 절이 이미 이를 인정하고 있어 **문서 안에서 서로 다른 말을 한다** |
| 2 | 계정을 지우면 "그 자리에서 사라집니다" | 복원(Time Travel·백업)으로 되살아난다. §6-2 |
| 3 | 계정 삭제로 "그 자리에서 지워지고" | 위와 같음 |
| 4 | 이전 국가: "미국을 포함한 Cloudflare 글로벌 네트워크 소재 국가" | 이것이 고지 요건상 충분한 특정인지 미확인 (L4) |
| 5 | "로그인을 진행하시면 동의하신 것으로 봅니다" | **현재 화면에 동의를 받는 자리가 없다.** 로그인 게이트에는 방침 링크조차 없고, 전면 게이트가 푸터의 방침 링크를 가린다 — **동의했다고 주장하는 바로 그 순간 방침에 닿을 수 없다** |
| 6 | 처리 근거를 "동의"로 단정 | L1 이 미확정. 계약 이행이면 이 문장이 틀린다 |
| 7 | 만 14세 제한은 "기술적 차단이 아니라 약속" | **사실과 맞다.** 다만 그 방식의 충분성이 미확인 (L6) |
| **8** | 「로그인 없이 둘러보기」는 아무 정보도 수집하지 않는다 vs 「남용을 막기 위한 처리」는 IP 기준 요약값을 센다 | **5판 발견.** 로그인 콜백 주소를 직접 열면 **로그인하지 않은 요청에도** `rate_limits` 행이 하나 생긴다(§2-2). **`RL_KEY` 가 production 에 등록된 2026-08-17 이후로 실제로 일어나는 일이다.** 방침의 두 절이 서로 다른 말로 읽히므로 **가입 화면 구현과 같은 변경 단위에서 함께 고친다** |

1·5·8 은 회원가입 화면 구현과 같은 변경 단위에서 반드시 고친다.

## 12. 검토 요청 질문

현재 범위는 **L1~L15** 다. 앞의 일곱은 2단계 결정서에서 정리한 것이고, L8 이후는 3단계 설계에서
새로 생겼다 — L11 은 2판, **L9 의 하위 질문 6개는 3판**, **L12 는 4판**,
**L13·L14·L15 는 5판**에서 추가됐다. 번호는 재사용하지 않는다(지운 질문이 있으면 번호를
비워 둔다 — 외부 검토자가 회신에서 번호로 지목할 수 있어야 하기 때문이다).

| # | 질문 | 왜 갈리는가 |
|---|---|---|
| **L1** | 단어장 동기화를 위한 제공자 회원번호·내부 번호·단어 목록 처리의 근거는 개인정보 보호법 **제15조 제1항 제1호(동의)** 인가 **제4호(계약의 이행)** 인가 | 「기기 밖 저장」이 서비스의 본질이라면 제4호일 수 있다. 제4호면 동의 체크박스가 오히려 부정확한 표시가 된다 |
| **L2** | L1 이 동의라면 **제22조 제1항의 구분 동의**를 어떻게 나누는가(필수/선택) | 별명은 선택 입력값이다. 선택 동의를 거부해도 서비스를 거부할 수 없다(제22조 제5항) |
| **L3** | Cloudflare 를 통한 국외 처리가 **제28조의8 제1항 제1호(별도 동의)** 인가 **제3호(계약 이행에 필요한 처리위탁·보관 + 방침 공개)** 인가 | 제3호면 별도 동의 화면이 필요 없다. 제1호면 가입 화면에 항목이 하나 는다 |
| **L4** | 제3호를 쓸 경우 **제28조의8 제2항의 고지 5항목**(이전 항목·국가·시기와 방법·받는 자·이용 목적과 보유 기간)을 어떻게 적어야 충분한가. 특히 **「이전되는 국가」를 특정할 수 없는 CDN 구조**에서 | 현재 표는 5항목 형태이나 국가가 특정되어 있지 않다 |
| **L5** | 계정 삭제 후 정책 이벤트(약관 수락·연령 진술)를 **보존할 근거가 있는가, 보존해야 하는가** | 답에 따라 DB 설계가 통째로 달라진다(§13) |
| **L6** | 법정대리인 동의 없이 만 14세 미만을 **배제**하는 현재 방식이 **제22조의2** 상 충분한가. "확인 수단이 없다"는 사실이 사업자 책임에 어떤 영향을 주는가 | 확인 수단을 만들려면 생년월일·본인확인이 필요한데 최소수집과 정면 충돌한다 |
| **L7** | 약관·방침을 가입 시점에 표시하고 그 시점을 기록하는 방식이 **정보통신망법** 등 다른 법령상 요구와 충돌하거나 부족한 부분이 있는가. **결제·거래가 없는 이 서비스에 법령상 별도 보관 의무가 존재하는가** | 우리는 광고성 정보를 보내지 않는다는 **사실**만 안다. 그것이 제50조 적용 여부에 어떤 영향을 주는지는 **판단하지 않았다** |
| **L8** | 약관·방침 **전문을 열지 않고 체크박스만 체크**한 것을 「수락」으로 기록해도 되는가. 전문 열람을 강제해야 하는가 | 설계는 두 경우를 모두 지원할 수 있다. 강제 여부에 따라 UI 가 달라진다 |
| **L9** | 삭제 표식(**내부 계정 번호의 HMAC 값**)의 성격과 보유기간. **하위 질문 6개는 아래 §12-2** | 복원된 DB 와 대조하면 특정 가능하므로 익명정보로 보지 않고 있다. **보유기간이 상태(confirmed / pending)에 따라 다르다** |
| **L10** | **삭제 후 복원으로 데이터가 되살아날 수 있다는 사실**을 방침에 어떻게 적어야 하는가. 「즉시 삭제」와 「복구 이력 보유기간」을 어떻게 함께 표현해야 오인이 없는가 | 현재 방침의 "그 자리에서 사라집니다"는 복원 시 사실과 달라진다(§10 의 2·3) |
| **L13** | **제공자 회원 고유번호가 「이 서비스 전용 값」인지가 확정되지 않았다**(§2-3). 구글 `sub` 는 공식 문서상 **계정 단위 전역 식별자**로 읽히고, 카카오·네이버는 공식 문서를 확인하지 못했다. 이 값이 다른 서비스와 대조 가능한 값일 경우 **가명정보·식별 가능성 판단과 방침 문구가 달라지는가.** 확인 자체를 사업자 의무로 보아야 하는가 | 「대조 불가능」을 근거로 위험이 낮다고 적어 온 문장이 여러 곳에 있었다. 근거가 없으면 그 문장을 전부 내려야 한다 |
| **L14** | **삭제 표식의 보유기간을 Time Travel 만 보고 정할 수 없다**(§12-2). 수동 백업도 과거 계정을 되살린다. 표식보다 **오래된 백업이 하나라도 남아 있으면 표식 보유기간은 부족**하다. 「표식 보유기간 ≥ 되살릴 수 있는 모든 경로의 최대 나이」를 **의무로 보아야 하는가**, 아니면 백업 쪽을 폐기·복원 금지로 묶는 것으로 갈음할 수 있는가 | 산식이 `max(Time Travel 최대 기간, 실제 복원 가능한 수동 백업의 최대 나이) + 안전 여유` 로 바뀌었다. 어느 항이 법적 기준인지에 따라 최종 숫자가 달라진다 |
| **L15** | **가입 정보를 암호화해 OAuth 제공자 URL 로 통과시키는 것**(§12-4). 약관 수락·연령 진술·행위 시각이 담긴 값이 카카오·네이버·구글의 주소와 접근 로그를 지나간다. 암호문이라 제공자는 내용을 읽을 수 없다. ① 이 통과 자체를 **제3자 제공·국외 이전으로 보아야 하는가** ② 방침에 고지해야 하는가 ③ 암호화가 아니라 **아예 통과시키지 않는 설계**(로그인 후 별도 수집)를 요구할 수준인가 | 3판까지 이 값은 **평문**으로 통과했다. 4판에서 발견해 5판에서 암호화로 바꿨다. 암호화가 법적 판단을 바꾸는지는 우리가 판단하지 않는다 |
| **L11** | **약관 수락·연령 진술의 「시점」을 어느 시각으로 보아야 하는가.** 사용자가 체크하고 가입 버튼을 누른 시각인가, 소셜 로그인이 끝나 DB 에 기록된 시각인가. 그리고 **체크는 했지만 로그인이 실패해 기록이 남지 않은 경우**를 어떻게 보아야 하는가 | 아래 §12-1 참조. 설계는 **두 시각을 모두 기록**하도록 되어 있어 어느 쪽이 답이어도 대응할 수 있다. 다만 **어느 쪽이 법적 증거인지**는 판단이 필요하다 |

### 12-1. L11 의 사실 관계 — 두 시각이 벌어지는 이유

도입 예정인 가입 흐름은 아래 순서다. **두 시점 사이에 소셜 로그인 왕복이 끼어 있다.**

```
① 사용자가 약관·연령 체크박스를 선택하고 [가입하기] 를 누른다      ← 행위 시각
     ↓  (서비스 서버가 이 시각을 자기 서명값 안에 기록해 들려보낸다)
②  카카오·네이버·구글의 동의 화면. 사용자가 얼마나 머물지 알 수 없다
     ↓  (최대 10분. 그 뒤에는 요청이 만료되어 처음부터 다시 해야 한다)
③ 로그인이 끝나고 계정과 기록이 DB 에 저장된다                      ← 기록 시각
```

| 사실 | 내용 |
|---|---|
| 정상 간격 | 수 초 ~ 수 분 |
| 최대 간격 | **10분**(그 뒤 만료) |
| 두 시각 모두 | **서비스 서버의 시각**이다. 사용자 기기의 시계나 사용자가 보낸 값이 아니다 |
| **서명이 증명하는 것** | ① `state` 내용이 **서버 발급 후 변조되지 않았다** ② 그 시각값이 **서버가 기록한 것**이다 |
| **서명이 증명하지 못하는 것** | ① `state` 가 **한 번만 사용되었다** ② 체크박스를 누른 사람과 **최종 OAuth 계정의 소유자가 동일하다** ③ **동시 재사용이 없었다** |
| 그래서 추가하는 것 | 위 ①을 위해 **가입 state 의 1회 소비 표식**(`state_hash` + 만료 시각)을 도입한다 — 아래 §12-3 · 질문 **L12** |
| **②에서 이탈하면** | **아무 기록도 남지 않는다.** 체크는 했지만 계정이 만들어지지 않았으므로 저장할 대상 자체가 없다 |
| 계획 | 두 시각을 각각 `occurred_at`(①) · `recorded_at`(③) 으로 **모두 저장**한다 |

**질문**: 「동의·수락·진술이 있었던 시점」의 증거로 ①과 ③ 중 무엇을 보아야 하는가.
방침·약관에 표시해야 한다면 어느 쪽인가. ②에서 이탈한 경우(기록 없음)에 법적 쟁점이 있는가.

### 12-2. L9 의 사실 관계 — **표식은 두 가지 상태이고 보유기간이 서로 다르다**

**먼저 기술적 사실만 적는다. 적정성 판단은 하지 않는다.**

| 사실 | 내용 |
|---|---|
| 표식의 내용 | **값 하나** — 내부 계정 번호(UUID)를 전용 비밀키로 HMAC 한 문자열. 그 외에 시각·상태·키 버전만 있고 제공자 ID·이메일·별명·단어장은 없다 |
| 왜 남기나 | D1 Time Travel·백업 **복원으로 되살아난 계정을 다시 지우기 위해서**다. 표식이 없으면 되살아난 사람을 식별할 방법이 없다(§10) |
| 상태 ① **confirmed** | 주 DB 삭제가 **확정된** 표식. 복원 시 반드시 다시 지워야 한다 |
| 상태 ② **pending** | 삭제를 시도했으나 **성공 여부를 모르는** 표식. 자동으로 지우면 "삭제는 됐고 확정만 실패한" 경우가 사라져 복원 때 되살아난다 |
| confirmed 의 보유기간(계획) | `확정 시각 + 복원 가능 최대 기간 + 안전 여유` |
| **산식** (5판 개정) | `expires_at = confirmed_at + max(TIME_TRAVEL_WINDOW, BACKUP_MAX_AGE) + SAFETY_MARGIN` |
| ⚠️ **왜 `max` 인가** | 4판까지는 Time Travel 만 보고 `MAX_RESTORE_WINDOW + SAFETY_MARGIN` 이라고 적었다. **틀렸다.** 계정을 되살리는 경로는 **둘**이고(§6-2), **수동 백업도 똑같이 되살린다.** 표식보다 **오래된 백업이 하나라도 복원 가능한 상태로 남아 있으면** 그 백업을 복원한 순간 표식은 이미 지워져 있어 **아무도 재삭제하지 못한다.** 그러므로 둘 중 **긴 쪽**을 써야 한다 |
| 항 ① `TIME_TRAVEL_WINDOW` | D1 이 복원해 주는 최대 과거 구간. 공식 문서: **무료 7일 / 유료 30일**. **우리 플랜은 대시보드에서 확인하지 못했다** |
| 항 ② `BACKUP_MAX_AGE` | **실제로 복원할 수 있도록 보관 중인** 수동 백업의 최대 나이. 현재 운영 규칙은 「migration 직전 생성 · 24시간 뒤 삭제 · 7일 상한」(§6-2)이므로 **규칙대로면 7일**이다. **다만 규칙이 지켜지는지 확인하는 수단이 없다** |
| 항 ③ `SAFETY_MARGIN` | **7일.** 복원 결정과 실행 사이의 시간, 시계 오차, 운영자가 주말에 알아채는 경우 |
| **현재 계산 결과** | 보수적 가정(Time Travel 30일 · 백업 7일)으로 `max(30, 7) + 7 = **37일**`. ⚠️ **이것은 기술적 계획값이고 확정 보유기간이 아니다** |
| ⚠️ **확정하지 않는 이유** | 세 항 중 **둘이 미확인**이다 — 플랜(7/30일)과 백업 규칙 준수 여부. 그리고 셋을 다 확인해도 **법적 적정성은 별개**다(L9-2·L9-3·L9-3b·**L14**) |
| **따라서 방침에 쓰지 않는다** | `privacy.html` 에 「14일 뒤 삭제」·「37일 뒤 반드시 삭제」 같은 **단정 문장을 넣지 않는다.** 세 항이 확정되고 법률 검토가 끝난 뒤에 문장을 만든다 |
| 짝이 맞아야 하는 규칙 | ① 표식보다 **오래된 수동 백업은 복원할 수 없게 폐기**하거나, 폐기할 수 없으면 **restore 금지 대상으로 분류**한다 ② 백업이 표식보다 오래 남는 운영이 실제로 있다면 **표식 기간이 부족한 것**이므로 표식 쪽을 늘린다. **백업 쪽을 줄이는 것과 표식 쪽을 늘리는 것 중 무엇을 택할지는 L14 의 질문이다** |
| ⚠️ 3판까지의 오기 | `7일 + 30일` 로 적혀 있었다. **두 항의 이름이 뒤바뀐 것**이고, 안전 여유는 30일이 아니라 **7일**이다. 4판에서 정정했다 |
| `SAFETY_MARGIN` 7일의 근거 | 복원 결정과 실행 사이의 시간, 시계 오차, 운영자가 주말에 알아채는 경우. 수동 백업 상한 7일(§10)과 같은 값 |
| pending 의 보유기간(계획) | **정해지지 않았다.** 자동 만료·자동 삭제를 하지 않는다. `pending_at + 24시간`을 넘기면 **운영 검토를 시작**하고, 검토 결과 「계정이 없다」면 confirmed 로 승격되어 위 산식이 적용된다 |
| pending 이 오래 남을 수 있는 경우 | 삭제 saga 가 중간에 실패했고 사용자도 재시도하지 않은 경우. 이때 표식은 **사람이 판정하기 전까지 남는다** |

**질문**:

| # | 질문 |
|---|---|
| **L9-1** | 이 표식(HMAC 값 + 시각 + 상태 + 키 버전)은 개인정보인가, **가명정보**인가, 익명정보인가. 현재는 「복원된 DB 와 대조하면 특정 가능」하다는 이유로 **익명정보로 보지 않고** 있다 |
| **L9-2** | **미확인 항이 둘인 상태에서 보수적으로 긴 값을 가정하는 방식**이 적정한가. 즉 실제 복원 가능 기간(플랜)과 실제 백업 나이를 모를 때 **긴 쪽을 가정해 더 오래 보관하는 것**이 최소보유 원칙과 충돌하지 않는가 |
| **L9-3** | 플랜이 **무료(7일)** 로 확인되고 백업 규칙(7일)도 지켜지는 것이 확인되면 산식은 `max(7, 7) + 7 = **14일**` 이 된다. **그때 14일로 줄여야 하는가**, 아니면 유료 전환 가능성·운영 단순성을 이유로 더 긴 값을 유지해도 되는가 |
| **L9-3b** | **안전 여유 7일**이 적정한가. 복원 결정과 실행 사이의 시간·시계 오차·운영자가 주말에 알아채는 경우를 덮으려는 값이다 |
| **L9-4** | **pending 표식을 자동 삭제하지 않고 사고 조사·수동 해결 때까지 보관**하는 것이 적정한가. 기술적으로는 이것이 가장 안전하지만 보관기간이 사전에 정해지지 않는다. **그리고 「삭제를 시도했으나 실패한 요청」의 기록 자체를 보존해야 할 의무가 있는가** — 있다면 지우는 대신 `aborted` 같은 별도 상태로 남겨야 한다 |
| **L9-5** | **unresolved pending 의 법적 최대 보관기간을 별도로 정해야 하는가.** 정해야 한다면 그 기간이 지났을 때 「그냥 삭제」 외의 대안(예: 사람이 판정 후 삭제)을 요구할 수 있는가. **pending · aborted · confirmed 세 상태의 보유기간을 각각 어떻게 정해야 하는가** |
| **L9-6** | 처리방침에 **Time Travel · 수동 백업 · 삭제 표식 저장소** 세 가지를 각각 어떻게 고지해야 하는가. 이용자에게 「즉시 삭제」와 「복구 이력 보유기간」을 함께 설명하는 문장이 필요한가 |

> **이 문서는 위 질문에 답하지 않는다.** 37일은 **미확인 항 둘을 보수적으로 가정한 기술적
> 계산값**이지 확정 보유기간도, 법적 적정성 판단도 아니다. **방침 문구로 쓰지 않는다.**

### 12-3. L12 의 사실 관계 — **가입 state 의 1회 소비 표식** (4판 신설)

**먼저 사실만 적는다.** 이 항목은 §12-1(L11)의 「서명이 증명하지 못하는 것」에서 나왔다.

| 사실 | 내용 |
|---|---|
| 무엇을 막으려는가 | **한 번의 약관 수락·연령 진술이 여러 계정의 증거로 기록되는 것** |
| 어떻게 그런 일이 생기나 | 가입 요청을 나르는 서명값(`state`)에 수락·진술·시각이 들어 있는데, **서버가 그 값을 한 번 썼는지 기록하지 않는다.** 같은 값을 실은 요청 두 개가 거의 동시에 도착하면 둘 다 통과할 수 있고, 각각 **다른 소셜 계정**으로 인증하면 계정이 둘 생긴다 |
| 결과 | 계정 A 와 B 에 **같은 수락 시각·같은 문서 해시**가 기록된다. 실제 행위는 한 번인데 증거는 둘이 된다 |
| 대응(설계) | 가입이 **성공적으로 처리될 때** 그 요청값의 **단방향 해시 하나**를 표에 남기고, 같은 해시가 이미 있으면 **거부**한다 |
| 저장하는 값 | **세 칸** — ① 요청값 전체를 **전용 비밀키로 HMAC** 한 문자열 ② 그 요청의 만료 시각(발급 후 10분) ③ 키 버전 |
| **저장하지 않는 값** | 서명값 원문 · 제공자 회원번호 · 내부 계정 번호 · 이메일 · **IP** · 별명 · 단어장. **누가 가입했는지 이 표만으로는 알 수 없다** |
| 언제 쓰나 | **소셜 로그인 검증이 성공한 뒤**에만 쓴다. 가입 화면을 반복해서 열거나 위조된 값을 보내는 것만으로는 아무것도 저장되지 않는다 |
| 보관기간(계획) | **그 요청의 만료(10분)가 지난 뒤 삭제**한다. 그전에 지우면 막으려던 중복이 다시 가능해진다. ⚠️ **「10분 뒤 삭제」는 삭제 가능 시점이지 실제 최대 저장기간이 아니다** — 정리 작업이 실제로 도는 주기(계획 1시간)를 더해야 한다(설계서 §10-5-2 의 용어 표) |
| 성질 — **말할 수 있는 것** | 되돌릴 수 없다(단방향). 이름·번호·IP 등 사람을 직접 가리키는 값이 **들어 있지 않다**. 전용 키를 모르면 **관찰한 요청값으로 이 표의 어느 행인지 맞춰 볼 수 없다** |
| 성질 — **말할 수 없는 것** | 「개인정보가 아니다」라고 **단정하지 않는다.** 이 표는 **특정 가입 시도가 실제로 계정 생성까지 갔다는 사실**을 10분간 남기는 처리 기록이다. 키를 가진 사람은 관찰한 요청값과 대조할 수 있다. 법적 분류는 **L12 의 검토 대상** |

**질문 L12**:

> 가입 요청의 replay tombstone(`state_hash`, `expires_at`)을 **약관·연령 진술의 계정 귀속
> 무결성**을 위해 **단기간(10분 수준)** 저장하는 것이 적정한가. 이 최소 보안 메타데이터를
> **처리방침에 표시해야 하는가.** 표시한다면 어느 절에 어떤 문장으로 적어야 하는가.
> 저장하지 않는 편이 낫다는 판단이라면, **같은 무결성을 다른 방법으로 확보해야 하는가.**

> ⚠️ **5판 정정 — 표식 값의 종류가 바뀌었다.** 4판은 이 값을 「서명값 전체의 SHA-256」이라고
> 적었다. 5판에서 **전용 키를 쓴 HMAC** 으로 바꿨다. 이유는 아래 §12-4 의 표에 있다 —
> 요약하면, 단순 SHA-256 은 **제공자 로그나 브라우저 기록에서 원래 `state` 문자열을 본 사람이
> 그 값을 직접 해시해 DB 의 표식과 맞춰 볼 수 있다.** 키가 있으면 그 대조가 불가능해진다.

### 12-4. L15 의 사실 관계 — **가입 정보가 제공자 URL 을 지나간다** (5판 신설)

**이 항목은 4판까지 자료에 없었다.** 4판 검토 중 발견해 5판에서 설계를 바꿨고, 그 사실과
바뀐 내용을 여기 적는다.

#### 무엇이 문제였나

가입 요청을 나르는 `state` 값은 **서명은 되어 있지만 암호화되어 있지 않았다.**

> 서명과 암호화는 다른 것이다. **서명은 봉투에 도장을 찍는 것** — 내용을 바꾸면 들키지만
> **누구나 읽을 수 있다.** **암호화는 봉투를 잠그는 것** — 열쇠 없이는 못 읽는다.
> 4판까지의 설계는 도장만 찍고 있었다.

이 값은 아래 자리를 **전부 지나간다.**

| 지나가는 곳 | 무엇이 남나 |
|---|---|
| 카카오·네이버·구글의 인증 주소 (`?state=…`) | 제공자의 **접근 로그** |
| 사용자 브라우저의 주소창·방문 기록 | 기기에 남는다. 같은 기기를 쓰는 다른 사람이 볼 수 있다 |
| 그 사이의 중간 프록시·보안 장비 | 조직 네트워크라면 남을 수 있다 |
| 사용자가 링크를 복사해 남에게 보내면 | 받은 사람이 본다 |

4판 설계대로면 그 값에 **약관 수락 여부 · 만 14세 진술 · 정책 문서 해시 · 행위 시각**이
Base64URL 로만 감싸여 들어간다. 한 번 풀면 「이 사람이 몇 시 몇 분에 만 14세 이상이라고
진술했다」가 그대로 나온다.

#### 5판에서 바꾼 것

| 항목 | 4판 (평문 서명) | 5판 (인증된 암호화) |
|---|---|---|
| 방식 | HMAC 서명 + Base64URL | **AES-GCM(AEAD)** 로 암호화하고 봉인 |
| 키 | `STATE_KEY`(로그인과 공용) | **`SIGNUP_STATE_KEY` 전용** — 로그인용과 분리 |
| 제공자가 보는 것 | **수락·진술·시각이 그대로 읽힌다** | **의미 없는 암호문**. 길이와 존재만 보인다 |
| 복호화 실패 시 | — | **가입을 진행하지 않는다**(fail-closed). 오류 응답에 내용을 싣지 않는다 |
| 로그인 `state` | 같은 형식 | **그대로 둔다** — 담는 값이 「제공자 이름·복귀 주소·만료·표 해시」뿐이라 읽혀도 되는 값이다 |

#### 그래도 남는 사실

| 사실 | 내용 |
|---|---|
| 제공자는 **암호문을 본다** | 내용은 못 읽지만 **값 자체는 로그에 남는다.** 길이·존재·시각이 관찰된다 |
| 제공자는 **가입이 일어났다는 사실**은 안다 | 그건 OAuth 의 성질이지 이 설계의 문제가 아니다 |
| 우리가 **못 하는 것** | 제공자 로그에서 그 값을 지우는 것 |
| 대안 | 통과 자체를 없애려면 **로그인을 먼저 끝내고 그 뒤에 별도 화면에서 수락을 받는** 설계가 된다. 기술적으로 가능하지만 「가입 = 한 번의 흐름」이 깨진다 |

**질문 L15**:

> ① 약관 수락·연령 진술이 담긴 값을 **암호화한 상태로** OAuth 제공자의 주소와 로그를
> 통과시키는 것이, 개인정보의 **제3자 제공 또는 국외 이전**에 해당하는가.
> 암호문이어서 제공자가 내용을 읽을 수 없다는 사실이 그 판단을 바꾸는가.
> ② 해당한다면 **처리방침에 어떻게 고지**해야 하는가.
> ③ 암호화로 충분하지 않고 **아예 통과시키지 않는 설계**(로그인 후 별도 수집)를 요구할
> 수준인가. 요구된다면 그 설계로 바꾼다 — 아직 구현이 없어 지금이면 바꿀 수 있다.

**함께 보시면 좋은 자료**: `worker/schema.sql`(저장 항목 전부) · `privacy.html`(현재 방침) ·
`docs/STAGE2_ACCOUNT_PRIVACY_DECISIONS.md`(정책 결정 배경) ·
`docs/STAGE3_SIGNUP_SECURITY_DESIGN.md`(가입·삭제 설계).

## 13. 검토 결과에 따라 바뀌는 지점

검토가 어느 쪽으로 나든 **출시 전에 바꿀 수 있는 상태**다. 구현이 아직 없기 때문이다.

| 질문 | 바뀌는 곳 |
|---|---|
| **L1 · L2** | `policy_events` 의 허용 조합(`CHECK`) · migration 파일 · 가입 화면 체크박스 개수 · 방침의 「처리 근거」 문장 · 동의 철회 경로의 존재 여부 |
| **L3 · L4** | 가입 화면의 국외 이전 항목 유무 · `xborder` 이벤트 유무 · 방침 국외 이전 표의 문장 |
| **L5** | **가장 크다.** 보존이 필요하면 `policy_events` 가 계정 테이블을 외래키로 참조할 수 없다. 현재 코드는 「계정 삭제 = 한 문장 + 전체 연쇄 삭제」이고 자동 검사가 그 구조를 강제하고 있어, 보존이 필요하면 **가명 키를 쓰거나 별도 저장소로 옮기는 재설계**가 된다 |
| **L6** | 연령 확인 방식 · 가입 화면 문구 · 방침 「어린이」 절 |
| **L7** | 보유기간 표 · 방침에 법령상 보관 의무를 어떻게 적을지(현재 문장은 확인되지 않은 판단을 담고 있어 그대로 쓸 수 없다) |
| **L8** | 가입 화면에서 [전문] 클릭을 체크박스 활성 조건으로 둘지 |
| **L9(L9-1~L9-6) · L10** | 삭제 표식 저장소의 도입 여부 · **confirmed 보유기간(현재 계획 `30+7=37`일)** · **무료 플랜 확인 시 14일로 줄일지** · **pending·aborted 의 보관기간과 처리 방법** · 방침의 삭제/복원 관련 문장 · 이용약관의 관련 조항 |
| **L12** | **가입 state replay tombstone** 의 도입 여부와 보관기간 · 처리방침에 표시할지 여부 · 표시한다면 어느 절에 어떤 문장으로 |
| **L11** | `policy_events` 의 시각 컬럼 구성 · 방침·약관에 표시할 시점 · 가입 중단 시 처리 |
| **L13** | 방침의 「계정 고유 번호」 설명 문장 · 이 값의 가명/식별 가능성 판단 · 카카오·네이버 공식 확인을 사업자 의무로 볼지 여부. **코드는 안 바뀐다**(이미 밖으로 내보내지 않는다) |
| **L14** | **`CONFIRMED_RETENTION` 의 최종 숫자** · 수동 백업 운영 규칙(폐기 시점·상한)의 강제 여부 · 표식보다 오래된 백업의 restore 금지 분류 · 방침의 보유기간 문장 |
| **L15** | **가입 state 의 암호화 유지 여부** · 방침의 국외 이전·제3자 제공 절 · 최악의 경우 **가입 흐름 자체를 「로그인 후 수락」으로 재설계**(§12-4 의 ③) |

## 14. 이 문서가 하지 않은 것

법률 결론 · 적합성 판정 · 조항 해석 · 「검토 완료」 표시. 위 §12 는 **질문이지 답이 아니다.**

이 문서에는 실제 사용자 식별자·세션·복구 링크·비밀값이 포함되어 있지 않다.
